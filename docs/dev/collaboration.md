# ToucanShelf 协作约定

- 状态：已生效
- 日期：2026-09-09（初稿）
- 参考：`huzhi-zhao.github.io` 仓库的同名文档。两处约定共享同一套底层规矩，
  差异只在各自的知识库结构与检出位置。

这份文档回答一个问题：**一段内容该写进 `docs/`，还是写进 ToucanShelf？**
以及在两边都能写的会话里，如何避免重复和漂移。

它描述的是当前有效的协作约定，属于常青文档：约定变了就原地更新，历史由 git 保存。

## 1. 本项目的检出

ToucanShelf 是本人的开源知识库项目，结构是 **workspace → 文件夹树 → 文档**。
文档在 API 里叫 `memo`，是完整文档不是便签。文件夹是路径前缀，写入一个不存在的路径
即自动出现，没有建文件夹这一步。

本项目的笔记在 `SideProjects` 知识库的 `CMOP` 文件夹，稀疏检出到仓库根的
`toucan-notes/`。它有自己的 git 仓库，被本仓库 gitignore，**不属于本仓库、不会被发布**。

注意本机存在**两个独立检出**：本项目的 `toucan-notes/`，以及站点仓库使用的
`~/Workspace/MemoBase/`。它们各有 `.memogit/`，不要混用。

## 2. 通道选择：本项目走 memogit

ToucanShelf 有两条通道，**同一篇文档在一个会话里只走一条，不要混用**。

| 通道 | 本项目的用法 |
|---|---|
| memogit 本地检出 | **默认。读、写、移动、重构全部走它** |
| MCP 在线工具 | 只在操作没有本地检出的知识库时使用 |

理由是 `memo_update_memo` 整篇替换、没有并发检查，改一处要先整篇读回再整篇写回，
一篇长笔记来回就是两趟全文传输；而且它看不到本地 git 快照。既然 CMOP 已经检出到本地，
就没有走 MCP 的必要。

节奏固定四步，完整手册见 `toucan-notes/.memogit/skill/SKILL.md`，**动手前必读**：

```bash
memogit pull            # 先拉，再动手
memogit status          # 自查
memogit push --dry-run  # 看计划
memogit push            # 同步
```

## 3. 会静默丢数据的规矩

- 文件末尾的 `<!-- memogit-id: memos/xxx -->` **绝不能碰**；新文件不要手写 ID。
- 移动或改名用 `mv`，**不要复制加删除**。后者会丢历史、评论和 ID。
- 不在文件顶部添加 memogit 头部。第一个 `---` 块永远属于用户的 frontmatter。
- `AGENTS.md`、`CLAUDE.md` 里的 `<!-- BEGIN memogit -->` 到 `<!-- END memogit -->`
  是 memogit 生成的脚手架，只在块外写自己的规则。
- 删除等于归档，可恢复，但**归档后的路径与标题仍被占用**，同名新建会失败。
- 标题里不放标点，标题会被 slugify 成锚点。
- 少写 ToucanShelf 方言：callout、`==` 高亮、`kanban` / `calendar` / `grid` 块、
  `.view.json`。用标准 Markdown，方言只在明确要求时写。
- `.memogit/config.yaml` 含访问令牌，不读出、不外传、不提交。
- 不在检出目录跑 `git push`，那个本地 git 仓没有 remote。

## 4. 文档引用语法

```
库内，库根相对：  [里程碑](/CMOP/milestone/README)
库内，文档相对：  [时间表](./时间表)      [问答库](../interview/问答库)
跨库，库限定：    [规格](@产品手册/fb/dc)
```

三条本项目实测确认的细节：

- **不带 `.md` 扩展名。** 服务器按标题寻址，写了扩展名会被它重写，下次 push 直接冲突。
- **中文不编码，保持可读；空格必须百分号编码。** 带空格的路径在第一个空格处截断，
  链接根本不成立。因此文件名一律用连字符不用空格，从源头避开这件事。
- **`CMOP` 前缀要写。** 本地检出剥掉了这一层，但链接解析在服务器侧，库根之下第一段
  就是 `CMOP`。

裸文本指针（`见 CMOP/milestone/MS-1`）不算引用，改结构时 grep 不干净也点不动，
一律写成链接。移动文档时服务器会自己固化正文里的相对链接，别手工模拟这套改写。

## 5. 不在这里维护目录地图

**`toucan-notes/` 的结构由它自己的 `README` 说了算。** 本文档只记录两边的分工，
不记录对面有哪些目录、哪些文档。

理由是同一份目录清单维护在两处必然漂移，最后是坏指针加三方打架。对面的结构变了不需要
改这里；分工变了才改这里。

## 6. 边界表：一段内容写哪边

| 内容 | 位置 |
|---|---|
| 系统边界、BO/BQ、数据契约、验收约束 | 仓库 `docs/dev/requirements/` |
| 长期约束后续开发的技术决策 | 仓库 `docs/dev/adr/` |
| 一次非平凡变更怎么实现、实际上线结果、事故复盘 | 仓库 `docs/dev/design|launch|postmortem/` |
| 当前可重复执行的操作步骤 | 仓库 `docs/guide/` |
| 项目跨会话任务队列 | 仓库根 `TODO.md` |
| Jira 式任务、问题与阻塞 | 笔记 `backlog/` |
| 周报 | 笔记 `weekly/` |
| 比 design 与 launch 更细的开发日志 | 笔记 `journal/` |
| 项目里程碑与个人取舍理由 | 笔记 `milestone/` |
| 脑爆，允许自相矛盾、写完就废 | 笔记 `brainstorm/` |
| 已想清但尚未稳定的技术判断 | 笔记 `keyfindings/` |
| 面试话术、模拟面试、岗位与雇主调研 | 笔记 `interview/`，**绝不进仓库** |
| 硬件与部署的实际配置 | 笔记 `config/` |
| 与本项目无关的通用方法论 | ToucanShelf `Engineering Playbook/`，两边都不放 |
| 身份、移民、语言、家庭 | MPNP 库，两边都不放 |

## 7. 路由规则：写哪边

判据按顺序问，第一个命中即定。

1. **是求职语境或私人材料吗？**（面试话术、岗位调研、薪资、个人取舍理由）
   → 笔记，**绝不进仓库**。
2. **是过程而不是结论吗？**（今天试了什么、为什么改主意、还没想清楚的想法）
   → 笔记。
3. **是任务、进度、阻塞、周报吗？**
   → 笔记。仓库根 `TODO.md` 只留项目级队列。
4. **是与本项目无关的通用方法论吗？**
   → ToucanShelf 的 `Engineering Playbook/`，不进本项目任何一边。
5. **其余，即已经定下来且外部读者需要它才能理解或复现本系统的事实**
   → 仓库 `docs/`，具体落点按 [docs/dev/README.md](README.md) 的路由顺序。

一句话版本：**`docs/` 放结论与约束，ToucanShelf 放素材与过程。**

## 8. 双向写作的规矩

两边都能写，最大的风险是同一件事被写两遍然后各自漂移。

1. **单一真源。** 每条事实只有一个权威位置，另一边只引用，不复制。
2. **引用只写位置，不搬内容。** 笔记里写「完整口径在
   `docs/dev/requirements/business-objectives.md`」，不把表格粘过去。
3. **链接单向。** 笔记可以引仓库路径；**仓库的任何文档不引笔记**，也不把笔记里的结论
   当作依据。这是 [docs/README.md](../README.md) 里「公开文档不得引用读者无法访问的
   私人笔记」的直接推论。
4. **决策回写。** 在笔记里讨论出的方向性结论，要回到 `docs/` 落一篇或改一篇，
   否则半年后会被无意识地改回去。冻结之后笔记只保留指针和个人理由。
5. **改前先读。** 任何更新都必须基于当前全文，不要凭记忆改。
6. **大改先商量。** 新建文档，或对已有文档做重构级别的改写（换结构、换定位、大段增删），
   先对齐写作范围和大体内容：写哪个路径、标题、分几节、每节讲什么，确认后再动笔。
   知识库是长期资产，位置和结构定错了，后面引用它的地方全跟着错。错字、补一条事实、
   更新链接这类局部修补不受此限，直接改即可。

## 9. 会话开场清单

需要跨两边工作时：

1. 确认通道：检出根在 `toucan-notes/`，走 memogit，不用 MCP。
2. `memogit pull`，再动手。
3. 要了解笔记结构，读 `toucan-notes/README`，不要依赖本文档的描述。
4. 产出内容前，用第 7 节的路由规则先决定写哪边。
5. 收尾：`memogit status` → `push --dry-run` → `push`。

## 10. 维护

本文档只维护**分工与通道规矩**，不维护对面的目录清单。分工变了改这里；
`toucan-notes/` 的结构变了，不需要改这里。
