# 批量支付报文的 Bronze 落地：组层、交易层与两处重复结构

> **Status**: Draft · **Date**: 2026-09-12
>
> **关联需求**：[监管与行业数据契约](../requirements/regulatory-data-contracts.md)
> §4A.3、§4A.4、§4A.5、§4B.2、§4B.4
>
> **关联 ADR**：[ADR 0002 事务中心的湖仓分层](../adr/0002-transaction-centric-lakehouse-layering.md)
>
> **关联架构**：[平台架构](../platform-architecture.md) §7 执行约束
>
> **执行状态**：未实现。本文是落地方案。

## Problem

**`pacs` 与 `sese` 的结构不同，Bronze 不能按同一种方式落。**

`sese` 一条报文一笔指令，落行即落事实。`pacs.008` 与 `pacs.009` 的 `CdtTrfTxInf`
基数是 **1..unbounded**，**一条报文里可以装任意多笔交易**。

由此产生的两难，[契约文档](../requirements/regulatory-data-contracts.md) §4A.3 已经点明：

- **按报文落行**，一行藏着 N 笔业务事实，Silver 只能靠解析数组还原。
- **按交易落行**，组层的 `GrpHdr` 无处安放，而 `NbOfTxs` 与 `CtrlSum` 的一致性校验
  （不变量 P1-1、P1-2）恰恰是组层的事。

**还有三件事让它比"拆成两张表"更复杂：**

1. **交易层之下还有一层重复结构。** `UndrlygAllcn`（底层分配）是 0..unbounded，
   而**六段链条闭合的判据 P1-4 就落在这一层**：每条底层分配的
   `RltdRefs/SctiesSttlmTxId` 必须命中一条 `sese.023` 的 `TxId`。
   **把它压进交易行的数组里，链条闭合就无法用一句连接表达。**
2. **`pacs.002` 的交易层零必填。** 19 个元素没有一个是必填的，
   组层的 `GrpSts` 也是选填。**一条什么状态都不带的状态回报是 schema 合法的**，
   落地方案不能假设任何字段一定有值。
3. **状态词表不在 schema 里。** `pacs.002` 里 23 个 `External*` 类型在 XSD 上
   只是 `minLength=1, maxLength=4` 的字符串，没有 enumeration。
   **Bronze 不能对这些列建枚举约束**，见 §4A.5 第 3 条。

**问题：这批报文在 Bronze 落成几张表、主键怎么定、按什么分区。**

## Constraints

1. **Bronze 保留来源语义与到达顺序**，见 [ADR 0002](../adr/0002-transaction-centric-lakehouse-layering.md)
   的分层表。**Bronze 不去重、不校验、不规范化**，那些都是 Silver 与业务校验层的事。
2. **增量写入必须是按主键的 `MERGE INTO`，不得纯 append**，见[平台架构](../platform-architecture.md) §7。
   **因此 Bronze 必须有一个稳定的主键**，否则这条约束无法遵守。
3. **每个事件同时携带业务发生时间与进入批次标识**，同上。迟到定义为后者晚于前者所属批次。
4. **不得改写已提交的历史分区。** 同上一节明记 T+1 迟到、更正与公司行为都会造成改写，
   分区键的选择必须把这件事挡在前面。
5. **`External*` 列不建枚举约束。** 合法性校验推到业务校验层，且依赖外部词表版本。
6. **表属性受[写入路径准入检查](2026-09-12-write-path-admission-checks.md)约束。**
   凡进入双写清单的表必须显式设 merge-on-read 并带维护排期。

## Plan

### 一、五张表，按重复结构的层级切

**切分依据是 schema 的基数，不是使用便利。** 每遇到一个 `unbounded`，就多一张表。

| 表 | 一行是什么 | 来源基数 | 覆盖报文 |
|---|---|---|---|
| `bronze_pacs_group` | 一条报文的组头 | 根下 `GrpHdr` 1..1 | `pacs.008`、`pacs.009` |
| `bronze_pacs_transaction` | 一笔贷记划拨 | `CdtTrfTxInf` 1..unbounded | 同上 |
| `bronze_pacs_underlying_allocation` | 一条底层分配 | `UndrlygAllcn` 0..unbounded | 同上 |
| `bronze_pacs_status_group` | 一条状态回报的原组信息 | `OrgnlGrpInfAndSts` 0..unbounded | `pacs.002` |
| `bronze_pacs_status_transaction` | 一笔交易的状态 | `TxInfAndSts` 0..unbounded | `pacs.002` |

**`pacs.002` 占两张表而不是一张，理由与前三张相同**：它的两个层级都是
0..unbounded，**组层状态可以完全缺席**，两者不是父子必然关系。

**`camt` 的三张报表不在本文范围内**，但它们共用同一个 `ReportEntry16`，
**明细解析可以复用一套**，见 §4A.7。本文的分层原则应当可以照搬，**照搬前要另行核实**。

### 二、主键：技术键，不是业务键

**这是本文最容易做错的一处决定。**

`GrpHdr/MsgId` 与 `PmtId/EndToEndId` 看起来都是天然主键。**用它们做 Bronze 主键是错的**，
因为 Bronze 要保留重复投递：同一条报文被投两次，是**必须留下的事实**，
[验证与对账规范](../requirements/validation-and-reconciliation-specification.md) §3
把"重复"列为一个差异类别，**去重发生在 Silver**。业务键做主键会把第二次投递吃掉。

**因此每一层的主键是"父键 + 序号"，最顶层的父键是到达标识。**

| 表 | 主键 | 说明 |
|---|---|---|
| `bronze_pacs_group` | `ingest_batch_id` + `source_file_id` + `record_ordinal` | 一个文件内第几条报文 |
| `bronze_pacs_transaction` | 组表主键 + `tx_ordinal` | `CdtTrfTxInf` 内的**位置** |
| `bronze_pacs_underlying_allocation` | 交易表主键 + `alloc_ordinal` | 同上 |
| `bronze_pacs_status_group` | 组表主键 + `grp_sts_ordinal` | — |
| `bronze_pacs_status_transaction` | 组表主键 + `tx_sts_ordinal` | — |

**序号必须是报文内的物理位置，不是任何业务字段的排序结果。**
理由有两条：一是 `pacs.002` 交易层零必填，**没有任何字段保证存在到可以排序**；
二是不变量 P1-1 比的是 `NbOfTxs` 与实际条数，**条数只有按位置计数才算得准**。

**这套主键让"重跑"与"重投"分得开，这正是它存在的理由。**

- **重跑同一批次**：`ingest_batch_id` 与文件内位置都不变，
  `MERGE INTO` 命中同一行，**结果逐行相同**，满足§4 的幂等断言。
- **数据里真的重投了一次**：新的到达标识，落成新行，
  **重复作为事实保留下来**，Silver 去重时能看见两次。

### 三、分区：按摄取批次，不按业务日期

**按 `IntrBkSttlmDt`（银行间结算日）分区是直觉答案，也是错的。**

迟到与更正会带来属于旧业务日期的新报文。按业务日期分区，
**每一次迟到都会改写一个已提交的历史分区**——正是[平台架构](../platform-architecture.md) §7
明令要挡住的那件事。而 T+1 场景下迟到不是例外，**是主业务流本身**。

**分区键：`ingest_date`（摄取批次日期）。**

- 到达一次就写一次，**历史分区只增不改**。
- 与"业务发生时间 + 进入批次标识"这条约束天然对齐。
- 迟到在数据上就表现为业务日期早于摄取日期，**不需要额外标记**。

**业务日期作为普通列保留并参与 Silver 的分区。** Bronze 按到达组织，
Silver 按业务组织，**两层的分区键不同是刻意的**。

**是否再加一级分区键，留作未决。** 候选是报文标识符（`pacs.008` / `009` / `002`）。
它的取值只有个位数，**分区数可控**，但日增量本来就小，
**过早分区会直接制造小文件**，而小文件治理已经是独立排期的作业。见 Open questions 第 1 条。

### 四、原始报文只存一份，存在组层

**每一层都带原始 payload 会把一条 N 笔的报文放大 N 倍。**

- **原始报文全文只落在 `bronze_pacs_group`。**
- 子层各行带**指回组表主键**的外键，以及**自身在报文内的位置路径**，
  例如 `CdtTrfTxInf[3]/UndrlygAllcn[2]`。
- **位置路径同时是排查手段**：任何一行都能凭它在原文里定位到那一段。

**这一条部分回答了 [ADR 0002](../adr/0002-transaction-centric-lakehouse-layering.md)
Open questions 里"Bronze 对原始 payload 的保留边界，以及解析后字段与原报文的关联方式"。**
**只是部分**：本文只覆盖 `pacs`，`sese`、`camt` 与 FIX 侧的同一问题仍然开放。

### 五、`External*` 列的落地口径

| 规则 | 理由 |
|---|---|
| 一律落成字符串，**不建枚举约束** | XSD 上就是 `minLength=1, maxLength=4` 的字符串 |
| 每行记录**生成时所用的 External Code Sets 版本** | 词表按季度版本化，见 §4A.9。不记版本，日后无法判断一个码当时是否合法 |
| 合法性判定不在 Bronze | 属于业务校验层，且该层依赖外部词表版本 |

**版本列不是可有可无的元数据。** 词表是季度更新的，
**同一个四字符码在不同版本里的合法性可以不同**。Bronze 不记，
校验层就只能拿"今天的词表"去判"当时的数据"，**那是错的判定**。

### 六、表属性

五张表**均不进入双写清单**：Bronze 由 Spark 写入，
单机引擎只读不写。因此它们**保留 copy-on-write 默认值**，
**不产生 delete 文件，也不需要 delete 文件的维护排期**，
见[写入路径准入检查](2026-09-12-write-path-admission-checks.md) 第二层。

**这一条要显式写下来，而不是靠"没列进清单"来表达**，
因为准入检查的第三层会报告清单外的表，**必须有一个地方说明它们为什么在清单外**。

## Rejected options

| 被否方案 | 理由 |
|---|---|
| 一张表，交易存成数组列 | 组内一致性校验还能做，但 P1-4 的链条闭合要靠展开数组再连接，**六段链条的判据不该藏在一次 explode 里** |
| 一张表，按交易落行，组头字段重复到每一行 | `GrpHdr` 冗余 N 份，且 `NbOfTxs` 与实际条数的比对退化成自证 |
| 用 `MsgId` 与 `EndToEndId` 做主键 | 会把重复投递吃掉，而重复是必须保留的事实，也是一个已定义的差异类别 |
| 按业务结算日分区 | 每次迟到都改写已提交的历史分区，与平台架构 §7 直接冲突，而迟到是主业务流 |
| 底层分配压进交易行 | 同第一条。它承载的是链条闭合判据，不是附属明细 |
| Bronze 就地去重 | 越层了。Bronze 保留来源语义，去重是 Silver 的职责 |
| `External*` 列建枚举约束 | schema 没有枚举，词表是季度版本化的外部件，约束会在换版当天批量拒绝合法数据 |

## Acceptance criteria

1. 五张表建出，主键与分区键与本文一致。
2. 一条含 N 笔交易的报文落地后，组表一行、交易表 N 行、序号从头连续。
3. 同一批次重跑，五张表逐行相同。
4. 同一条报文以两个不同到达标识投递两次，落成两组行，**都在**。
5. 迟到报文写入当日分区，**没有任何历史分区被改写**。
6. 每一行都能凭组表外键与位置路径在原始报文里定位到对应片段。
7. 每一行带 External Code Sets 版本。
8. 一条零字段的 `pacs.002` 能落地成功，**不因缺字段而失败**。

**第 8 条是刻意的。** Bronze 接受 schema 合法的一切，**判它有没有业务意义是下一层的事**。

## Open questions

1. **是否按报文标识符再分一级区。** 取值个位数，分区数可控，
   但日增量小，过早分区就是制造小文件。**倾向不分，等实测文件大小后再定。**
2. **序号从 0 还是从 1 起。** 无实质影响，但**必须全项目一致**，
   否则位置路径在不同层之间对不上。
3. **`camt` 能否照搬本文的分层。** 三张报表共用 `ReportEntry16`，看上去可以，
   **但余额元素的基数三张各不相同**，需要另行核实。
4. **`sese` 侧是否也要引入位置路径列。** 它一报文一指令，位置路径退化为常量，
   **但保留它可以让排查手段在两个族之间一致**。未决。
