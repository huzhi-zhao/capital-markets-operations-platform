## 1. 本文的作用与边界

本文规定**怎样判断一次运行的结果是对的**。它服务于主 BO：对账不平时能定位到笔，而不是
只报告总数不一致。

它不规定生成什么，那属于[生成规范](data-generation-specification.md)；也不规定怎么实现
检查，那属于 design。

## 2. 对账口径

### 2.1 四个域与比对关系

| 比对 | 左侧 | 右侧 | 主要用途 |
|---|---|---|---|
| R1 | 成交事件 | 持仓变动 | 数量是否传导 |
| R2 | 成交事件 | 现金流水 | 金额与费用是否传导 |
| R3 | 内部持仓 | 清算方持仓 | 与外部是否一致 |
| R4 | 内部现金 | 对手方对账单 | 与外部是否一致 |

R1 与 R2 是内部一致性，R3 与 R4 是外部一致性。两类的差异含义完全不同：内部不平是自己的
处理错误，外部不平可能是对方的错误或口径差异。**不得混在同一个异常队列里不加区分。**

### 2.2 时点基准必须逐对声明

**这是最容易出错的地方。** T+1 结算意味着 T 日的成交在 T+1 日交割，现金比成交晚一天。
若 R2 用同一个日期同时切两侧，结果是**全部不平**，而且看上去像是系统坏了。

因此每一对比对必须显式声明左右两侧各自的日期基准：交易日、结算日、还是入账日。**没有声明
日期基准的比对不允许上线**，这条比任何阈值都重要。

### 2.3 L-1 范围内的 R1 与 R2 具体化

L-1 冻结后，两组内部一致性比对可以写实。字段依据见
[监管与行业数据契约](regulatory-data-contracts.md) §3.3 与 §3.6。

| | R1 成交对持仓 | R2 成交对现金 |
|---|---|---|
| 左侧取数 | `ExecType=F` 的成交回报，按 `ExecID` 去重 | 同左 |
| 参与字段 | `LastQty(32)`、`Side(54)`、标的与账户 | `LastQty(32)`、`LastPx(31)`、`Currency(15)` |
| 聚合式 | 按买卖方向对 `LastQty` 求和 | 对 `LastQty × LastPx` 求和，再加费用 |
| 左侧日期基准 | `TransactTime(60)` 所属交易日 | `TransactTime(60)` 所属交易日 |
| 右侧日期基准 | **取决于持仓口径，见下** | **结算日，等于交易日加一** |
| 容差 | 零，数量不设容差 | 待定，仅允许因舍入产生 |

**R1 必须先声明比的是哪一种持仓。** 交易日持仓在成交当日变动，结算日持仓在 T+1 变动。两者
都是正确的持仓，但对不上同一批成交。**不声明就比，等于随机挑一种然后把另一种全报成差异。**

**R2 的两侧日期天然错开一天。** 左侧按交易日切，右侧必须按结算日切，映射关系是 T 到 T+1。
这是 §2.2 那条规则最直接的例子：两侧用同一个日期切，结果是全部不平。

### 2.4 容差

- **容差按比对对声明，不设全局默认值。** 零容差的比对必须显式写成零，不能靠"没配置"来
  表示。
- **容差只允许用于因舍入产生的派生金额。** 数量类差异**没有容差**，差一股也是差异。
- 每个非零容差必须写明理由与推导，不能只写数字。

### 2.5 确认层断言（C-1 范围内）

C-1 冻结后，确认覆盖面可以写实。它不是第五对比对，而是一条覆盖性断言：分配出去的账户
必须都收到确认，否则金额链条在确认段就断了，BQ-2 的解释链走不到结算。

| | 断言 | 强度 |
|---|---|---|
| 覆盖性 | 每个被分配的账户**至少**一条确认 | 无条件成立 |
| 唯一性 | 每个被分配的账户**恰好**一条确认 | **仅在 C-1 条件下成立** |

- 左侧取数：分配指令内的账户集合。右侧取数：确认报文，按账户归集。
- 日期基准按 §2.2 显式声明：两侧同取分配所属交易日，确认迟到属于跨批次问题，由差异分类
  的时间差类别处理，不在本断言内消化。
- 容差为零。这是计数类断言，按 §2.4 数量类不设容差。

**适用条件必须与断言同时落地。** 唯一性只在 C-1 的窄条件下成立：一次确认、不拆分、无更正
与取消。C-2 一旦引入部分确认或更正确认，同一账户出现多条确认就是**合法**的，此时唯一性会
从有效断言变成假阳性的来源。按 §6.1 末尾那条规矩，本断言登记它的失效条件：**C-2 落地时
唯一性必须降级为"每账户恰好一条有效确认"或直接删除，覆盖性不受影响。**

没有登记失效条件的断言不允许上线。理由与 §6.1 相同：假差异比漏报更致命，它让分析员停止
相信队列。

## 3. 差异分类

**每一条差异必须落入一个类别，"未分类"本身是一个类别并且必须被计数。** 把未分类的差异
隐藏起来，等于把最危险的那部分从视野里去掉。

| 类别 | 含义 | 典型来源 |
|---|---|---|
| 时点差异 | 两侧都对，只是尚未到达对方的时点 | T+1 结算错位 |
| 迟到 | 应到未到 | 迟到确认、迟到对账单 |
| 数量或金额不一致 | 两侧都有，值不同 | 更正、拆分成交 |
| 口径性差异 | 两侧按不同定义计算 | 两个官方汇率来源 |
| 重复 | 同一事件被计入多次 | 重投、重跑未幂等 |
| 缺失 | 一侧完全没有 | 漏发、过滤错误 |
| 未分类 | 不属于以上任何一类 | 必须计数并单独告警 |

**时点差异与迟到必须分开。** 前者是正常的，会在下一批自然消失；后者是异常的，需要人处理。
把两者合并会让异常队列里充满噪声，运营分析员就会开始忽略它，那时整个 BO 就失效了。

## 4. 可重跑验证

三条断言，强度递增：

1. **无错重跑**：批次重跑不报错。这是最弱的一条，单独成立没有意义。
2. **结果幂等**：同一批次重跑后，目标表的内容与首次运行**逐行相同**。用输出行的稳定哈希
   比对，不用行数或汇总值，后者会掩盖抵消性错误。
3. **种子可复现**：同一根种子、同一生成器版本、同一参考数据版本，产出完全相同，见
   [生成规范](data-generation-specification.md) §2。

**第 2 条必须在有迟到数据的批次上验证。** 在干净批次上验证幂等是没有信息量的：`MERGE INTO`
的正确性恰恰体现在有更新要写的时候。

### 4.1 来源独立性断言

对账要求两个独立来源。对手方对账单一旦由内部账本推导出来，两边必然对平，主 BO 随之失效，
见[原始数据源清单](raw-data-source-inventory.md) §2.2。

该约束的特殊之处在于**违反它不会产生任何报错**：管道照常运行，对账结果全绿，只是这个绿色
不再有意义。文档纪律拦不住它，因此它必须是一条自动断言：

- 对手方一侧与内部账本一侧的生成路径不得共享随机流，也不得读取对方的输出。
- 断言在生成阶段执行，失败即中止生成，不留到对账阶段才发现。
- 断言结果与其他门禁一样按 §5 记录，`not evaluated` 不计为通过。

具体实现形式随生成器一起确定；本节规定的是它必须存在及其失败语义。

### 4.2 时点正确性断言

BO-4 的特征表必须按时点切片，见[业务目标](business-objectives.md) §2.3。该文已规定成功标准
是这条链可复现而不是模型精度，本节规定怎样判定它成立。

三条断言：

1. **每行特征必须带一个显式的 as-of 时点**，构建时按该时点切片。没有 as-of 的特征表不允许
   进入训练。
2. **任何字段的生效时间晚于该行 as-of 的，不得进入该行。** 判据是字段的业务生效时间，不是
   它的写入时间；两者在有迟到数据的批次上会分叉，而那正是本项目最常见的批次。
3. **标签的观测时点必须严格晚于 as-of，且两者之差显式声明为预测视界。** 未声明视界的标签
   等于没有定义，因为"提前多久预测出来"决定了它有没有业务价值。

**与重述的交互是这条断言最容易破的地方。** 重述之后重建特征表，必须取 as-of 当时的版本，
不能取最新版本；后者会把重述结果倒灌进重述之前的训练样本，这是泄漏中最隐蔽的一种，且在
指标上只表现为"效果变好了"。时间旅行能力正是服务这条。

**失败语义是 fail，不是告警。** 泄漏的表现形式是分数变好，因此它永远不会自己暴露；按 §5，
未运行一律记 not evaluated 且不计通过。

**这条断言本身必须被证明有效。** 按 §6 的规矩，注入一个已知的泄漏特征，写明预期被上面哪条
捕获以及正确处理后的预期结果，否则无法区分"没有泄漏"与"检查没生效"。

## 5. 验收门禁

**门禁结果是三分类：pass、fail、not evaluated。**

**`not evaluated` 绝不能计为 pass。** 一项检查没跑，与它跑了并通过，是完全不同的两件事。
把两者混同是数据质量框架最常见也最致命的缺陷，因为它让缺失的覆盖面看起来像通过的覆盖面。

- 门禁**默认失败**。检查未运行、结果未回写、或状态无法判定时，一律记为 fail 或
  not evaluated，不得因缺少证据而放行。
- 每次门禁结果必须记录：检查标识、规则版本、数据版本、运行时间、结论。
- 门禁结果不得只存在于日志文本里，必须是可查询的结构化结果，见
  [平台架构](../platform-architecture.md) §9。

**新鲜度是门禁的一部分。** 批次未在[工作负载基线](../workload-baseline.md) §5.2 规定的窗口
内完成，即使所有数据检查通过也不算通过，因为异常队列没能在分析员到岗前就位。

## 6. 故障注入

**注入的目的是证明检查有效，不是证明系统能崩。** 每一类注入必须写明四项：注入位置、注入
比例、预期被哪条检查捕获、正确处理后的预期结果。缺少第四项的注入不是测试。

不依赖 FIX 证据、现在即可确定的注入类别：

| 注入 | 预期捕获者 |
|---|---|
| 批次迟到到达 | 时点差异与迟到的分类边界 |
| 同一批次重复投递 | 幂等断言与重复类别 |
| 整批缺失 | 缺失类别与门禁默认失败 |
| 反向合股后的持仓重述 | [生成规范](data-generation-specification.md) §7 第 3 条不变量 |
| 参考数据序列拼接边界的重复与缺口 | 口径性差异类别 |

### 6.1 L-1 的状态机违规注入

转移表已填，见[监管与行业数据契约](regulatory-data-contracts.md) §3.4。

| 注入 | 违反 | 正确处理后的预期结果 |
|---|---|---|
| 跳过接受回报，首条即成交 | L-1 步骤序列 | 整条订单链标为契约违规，不进入正常对账 |
| 首笔成交即全部成交 | L-1 要求至少三笔 | 同上 |
| `Filled` 之后继续发送成交 | L-1 终态 | 同上 |
| 派生字段与成交序列不符 | [生成规范](data-generation-specification.md) §6.1 | 数量与均价断言捕获，归入数量或金额不一致 |
| `ExecID` 重复 | 全局唯一性 | 归入重复类别，去重后结果不变 |
| 同一订单链内 `TransactTime` 逆序 | 链内严格递增 | 归入未分类并单独告警 |

**前三条是 CMOP 场景契约违规，不是 FIX 违规。** FIX 4.4 本身允许单笔全成，规范原文也明确
提醒"矩阵未展示某转移不代表 FIX 禁止它"。把它们标成 FIX 违规是错的，而且是会传染的错：
断言里写错一次，对外口径也会跟着说错。

**L-2 落地时必须删掉，不是保留。** 单笔全成届时成为合法路径，这条注入会从有效测试变成永久
的假阳性来源。**每一条场景契约类注入都必须登记它在哪个场景扩展后失效。**

**断言必须带适用条件。** 见同一文档 §3.6：把只在订单存活期间成立的等式写成无条件不变量，
会在正常的撤单订单上批量报出假差异。假差异比漏报更致命，因为它让分析员停止相信队列。
