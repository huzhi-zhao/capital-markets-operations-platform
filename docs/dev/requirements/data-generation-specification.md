## 1. 本文的作用与边界

生成契约回答一个问题：**凭什么相信这批合成数据？** 答案不能是"看起来像"，只能是三条可
检验的性质：分布可对照真实观测、业务不变量可自动验证、脏数据是按契约注入或来自真实来源
而非偶然产生的缺陷。

本文规定生成什么、按什么参数生成、以及生成结果必须满足什么。它不规定生成器如何实现。

**没有证据的参数保持空白。** 编一个"看起来合理"的分布，比留空更有害：留空是已知的缺口，
编造是未知的错误。

## 2. 可复现性契约

**同一输入必须产出同一输出。** 每一次生成运行由三项完全确定：

| 输入 | 说明 |
|---|---|
| 随机种子 | 单一根种子，各子生成器的种子由它派生，不独立设置 |
| 生成器版本 | 代码提交号 |
| 参考数据版本 | `data/reference/sec/manifest.json` 的抽取日期 |

**每一行产出必须可归因到这三项。** 做不到就无法回答"上次那个结果是怎么来的"，而
[业务目标](business-objectives.md) §4 的第一条验收方向正是同一输入重复运行结果一致。

派生而非独立设置子种子，是为了让"改一个参数"不会静默地改变无关数据的取值。

## 3. 标的维度

**标的宇宙固定为 12505 个**，等于十年窗口内的真实申报人集合，见
[原始数据源清单](raw-data-source-inventory.md) §5.6 与 §5.7。它不是自由参数。

每个合成标的通过别名映射表一对一绑定到一个真实申报人。生成器从真实申报人那里继承的只有
**生命周期与事件日历**，不继承名称、代码或任何真实标识符：

| 属性 | 来源 |
|---|---|
| 上市起始 | 该申报人的首次申报日期 |
| 退市日期 | 该申报人的 Form 25 日期，若有 |
| 更名次数 | 该申报人的 `formerNames` 条目数 |
| 更名时点 | **不继承**，见下 |
| 代码、名称、行业等 | 生成值 |

**这构成一个真实驱动的缓慢变化维。** 标的维度的 SCD Type 2 版本链不是设计出来的演示，
它的变更**次数与存在性**来自真实申报记录。

**但更名日期不能直接继承。** 实测证明 `formerNames` 的 `from` 与 `to` 是该名称在 EDGAR
记录中出现的首末时点，随申报活动漂移，不是更名生效日：区间只有 2.6% 相互衔接，27.4% 的
多次更名者存在区间重叠，最新一条的结束时点还会漂向当下。证据见
[原始数据源清单](raw-data-source-inventory.md) §5.8。因此更名次数按真实回放，更名时点由
生成器在该标的的存续区间内按契约分配，并在文档与对外口径中标注为合成。

**交易事实必须服从标的生命周期。** 上市之前不得有成交，退市之后不得有成交，更名时点前后
的名称必须与当时的维度版本一致。这三条是标的维度上最容易被生成器违反的约束，必须作为断言
而非注释存在。

## 3A. 账户维度

**定于 2026-09-10。** 该维度由 A-1 带出、被 C-1 卡住：`AllocAccount`(79) 在 Confirmation 上是
必填字段，没有账户维度就生成不出一条合法的确认报文，见
[监管与行业数据契约](regulatory-data-contracts.md) §3A.3。

### 3A.1 与标的维度最重要的一点不同：这个维度是自由参数

**标的宇宙 12505 不是设计出来的，它等于真实申报人集合**，见 §3。**账户维度没有对应的真实
来源**：EDGAR 没有账户，公开数据里也没有任何可以一对一绑定的账户集合。

**因此这里的每一个规模数字都是设定，不是继承。** 这个区别必须保留到对外口径里。标的维度可以
说"变更次数来自真实申报记录"，**账户维度不能这么说，说了就是假的**。可主张的是结构与约束
正确，不是规模真实。

### 3A.2 两层结构，以及它为什么不能压平

账户不是扁平集合，**分配的 N 个账户必须同属一个客户**。理由是业务的：一笔大宗成交按分配指令
拆到多个账户，这些账户是同一个机构客户的子账户；拆到互不相干的客户名下，在业务上不成立。

| 层 | 内容 | 版本化 |
|---|---|---|
| 客户 | 机构客户，账户的归属方 | 是，SCD Type 2 |
| 账户 | 可被分配的最小单位，归属唯一客户 | 是，SCD Type 2 |

**压平成单层会让 A-1 的账户采样失去约束**，生成器会跨客户拆分同一笔成交。这类数据不会触发
任何 FIX 校验，**因为 FIX 不知道账户归谁**，错误只会在业务对账时以"客户持仓对不上"的形式
出现，而那时根因已经离现场很远。

### 3A.3 规模参数：全部是占位值

**沿用 §6.2 的处理方式**：被论证的是约束与分布形状，不是具体数字；数字是占位值，Phase 1
量出行宽与查询代价后重定。

| 参数 | 取值 | 约束 |
|---|---|---|
| 客户数 | 2000 | 需大到客户层聚合非退化，小到每客户有足够账户可拆 |
| 每客户账户数 | 截断几何分布，均值 6，下界 1，上界 200 | 长尾必须存在，否则分配总是拆成相近份数 |
| 账户总数 | 约 1.2 万 | 由上两行派生，不独立设定 |
| 每笔分配的账户数 N | 2 至 5，偏小 | 见[监管与行业数据契约](regulatory-data-contracts.md) §3A.1 |

**账户总数与标的总数同量级是巧合，不要据此建立任何关系。** 两者的决定方式完全不同，一个是
实测集合大小，一个是设定值。

### 3A.4 生命周期事件：开立、关闭、改名、并户

前三类与标的维度同构，**第四类不是**，见 §3A.5。年化速率同样是占位值：

| 事件 | 年化速率 | 说明 |
|---|---|---|
| 开立 | 十年窗口内均匀铺开，约 40% 的账户在窗口起点已存在 | 起点已存在的那批没有开户事件，版本链从窗口左边界起 |
| 关闭 | 5% | 关闭后不得再有分配 |
| 改名 | 2% | 纯属性变更，产生新版本，键不变 |
| 并户 | 1% | 多对一，见下节 |

**开立与关闭同年发生的账户必须允许存在。** 短命账户是 SCD Type 2 最容易出错的输入，与 §6A
让更名聚集是同一个用意：**制造短区间，因为区间不重叠不留空隙那条断言正是在短区间上失效**。

### 3A.5 并户是这个维度的真问题

**开立、关闭、改名都是一对一的，SCD Type 2 直接表达得了。并户不是。** 账户 A 并入账户 B 时，
A 的版本链终止，而 A 的持仓与成本基础转到 B 名下。**单键上的版本链表达不了这个跨键的转移。**

**契约：并户绝不改写历史事实。** A 的分配、确认与成交继续引用 A，一条都不重写。维度侧在 A 的
末版本上置一个 `merged_into` 属性指向 B，形成一条可上溯的链。下游要跨并户求和时沿该链上溯，
**而不是回头把事实里的账户号改掉**。

**理由是本项目的核心主张。** 逐笔可追溯意味着 Bronze 的事实一经落地就不再变化；一旦允许并户
回写历史，"重跑同种子得到同结果"与"每一笔都能追到源"两条同时失效，**而且失效得很安静**。

**由此产生两个后果，都要写进断言：**

1. **§7 第 3 条要按并户链求值，不能逐账户求值。** 该条说公司行为后账户层面的总成本基础不变；
   若 A 在事件后并入 B，逐账户看 A 归零、B 变大，**看起来就是违反**。必须在并户链闭包上求和。
2. **`merged_into` 可以成链，也必须允许成链。** A 并入 B、B 后来并入 C 是正常业务。求值时要
   走到链尾，**不是只跳一跳**。

**标的维度没有这个问题，不是因为它更简单，而是因为它没建模合并。** 标的的生命周期继承自
EDGAR 申报人，只有起始与退市，并购重组没有进入模型。**两个维度在这一点上不对称，不要相互
类比。**

### 3A.6 FIX 侧的三个字段取值

账户维度要供给 FIX 报文，下列取值就此定案，枚举出处为 FIX 4.4 Volume 6：

| 字段 | 取值 | 理由 |
|---|---|---|
| `AllocAccount`(79) | 由根种子确定性派生的合成账号 | 与 §6.3 同一条规则，不得用随机 UUID |
| `AllocAcctIDSource`(661) | 99（Other，custom or proprietary） | 账号是合成的；填 BIC、DTCC 或 OMGEO 就是在**声称一个并不存在的注册来源** |
| `AllocAccountType`(798) | 1（carried on customer side of books） | CMOP 是买方分配流，账户是客户账户 |

**`AllocAccountType` 的枚举有个洞：1、2、3、4、6、7、8，没有 5**（V6 p. 273）。与
`AllocReportType` 从 3 起跳是同一类陷阱，**按连续整数取值的生成器会产出非法值**。

### 3A.7 与事实的绑定

**与 §6.5 同构，方向相同：** 分配与确认的 `TradeDate` 必须落在被引用账户的存续区间内。开立
之前与关闭之后不得存在分配，**并户之后不得再向被并入方分配**。

**这三条是账户维度上最容易被生成器违反的约束**，与 §3 末尾那三条的地位一样，必须作为断言
而非注释存在。

## 3B. 参与方维度

**定于 2026-09-12。** 该维度由 S-1 带出：结算段引入了 **Instructing Party**（账户持有方）与
**Executing/Servicing Party**（账务服务方）两个角色，**§3A 的两层结构里一个都没有**，
见[监管与行业数据契约](regulatory-data-contracts.md) §4.9。P-1 随后又带出付方代理行与
收方代理行两个角色。**四个角色一起处理，不逐段补。**

### 3B.1 先把问题问对：缺的是一个维度，不是四个角色

**第一个判断决定后面全部：角色不是实体。** 同一家托管行在 `sese.023` 里是账务服务方，
在 `pacs.009` 里可能就是付方代理行；同一家投资管理人在结算段是账户持有方，
在分配段是下达分配指令的一方。**按角色各建一张维度表，会把同一个机构存成四份**，
而它们之间的一致性再没有任何东西保证。

**因此结论是：加一个维度，承载机构实体；角色是事实侧的引用位置，不是维度侧的分类。**
这与 §3A 处理账户的方式一致——账户维度不因为它在 `AllocAccount` 与 `SfkpgAcct` 两个位置
出现就变成两张表。

### 3B.2 账户持有方不需要新东西，它可以从账户推出来

**这一条是本节最省事的部分，但理由必须写清，否则会被当成偷懒。**

`sese.023` 的 `SfkpgAcct/Id` 填的是该笔分配账户（契约 §4.6）。**账户在 §3A 里归属唯一客户**，
而 §3A.2 已经保证**一笔分配的 N 个账户必属同一客户**。因此：

**账户持有方 = 该结算指令所引账户的客户，由账户函数式地决定，不采样、不新增层级。**

**这不是巧合，是 §3A.2 那条约束的直接后果。** 如果当初压平成单层，这里就推不出来了——
一笔分配可能跨客户，账户持有方就没有唯一答案。**§3A.2 的收益在两个月后的这一节才兑现。**

**由此得到一条断言，必须与 §3A.7 的三条并列：**

- **同一笔分配派生出的全部结算指令，其账户持有方必须是同一个客户。**
  违反它意味着账户维度的归属关系被破坏了，**而 FIX 与 ISO 20022 都校验不出来**，
  理由与 §3A.2 末段相同。

### 3B.3 账务服务方与两个代理行需要新维度，因为没有任何东西能推出它们

**现有维度里没有任何字段说"这个账户存在哪家托管行"。** 它既不能从客户推出，
也不能从标的推出，**必须新增**。

| 层 | 内容 | 版本化 |
|---|---|---|
| 金融机构 | 托管行、经纪商、代理行、**存管机构**，一张表 | 是，SCD Type 2 |

**存管机构是 2026-09-12 补入的，它不是可选角色。** 规范的
`DeliveringDepositoryAndParty1Rule` 与其镜像要求：不带常设结算指令时，
**对手方一侧的存管机构与第一层结算方都是必填**，见
[监管数据契约](regulatory-data-contracts.md) §4C.7.1。CMOP 不生成常设结算指令，
**所以每一条结算指令与结算确认都要带它**。

**存管机构与其余机构同表不同类型。** 数量上一个市场一家即可，
**规范的指引说没有中央存管机构的市场用交易所代替**，量级与托管行完全不同。

**规模参数全部是占位值**，处理方式同 §3A.3 与 §6.2：

| 参数 | 取值 | 约束 |
|---|---|---|
| 机构总数 | 12 | 需大到同一客户的对手方不总是同一家，小到每家都有足够事实量可聚合 |
| 其中存管机构 | **1 家** | 单一市场只有一家。**它出现在每一条结算指令上，是全表连接最频繁的一行** |
| 每客户的账务服务方 | **1 家，固定** | 见 §3B.4 的简化及其代价 |
| 代理行取值 | 从同一张表里取，与账务服务方可以相同也可以不同 | 资金段的参与方是金融机构，不是终端客户，见契约 §4B.1 |

**12 这个数字的量级理由要说一句。** 它远小于客户数 2000，**所以机构维度是一张会被反复
连接的小表**，与标的、账户两个大维度性质不同。**Silver 的连接策略因此不同**，
但那属于实现，不在本文。

### 3B.4 一个简化及其代价：同一客户的全部账户由同一家机构服务

**这是设定，不是业务规律。** 真实机构会把不同账户放在不同托管行，多托管是常态。

**采用它的理由只有一条**：一笔分配的 N 个账户若分属不同托管行，
**那一笔就要拆成多批结算指令，分别发往不同的账务服务方**，链条从"一笔分配对一组指令"
变成"一笔分配对若干组指令"。**这会同时改变 S-1 的形状与 §2A 的 V2 级校验口径**，
而当前没有任何 BQ 需要它。

**代价要写下来，不能只记简化：**

- **多托管带来的那一类差异被排除了。** 同一笔交易在两家托管行的状态回报不同步，
  是真实运营里典型的差异来源，**CMOP 现在造不出这类素材**。
  这与 [ADR 0006](../adr/0006-fix-single-version-baseline.md) 里 FIX 单版本排除掉的
  口径性差异属同一类已知缺口。
- **解除这条简化不是加一列，是改链条形状。** 届时 S-1 的"一笔分配对一组指令"要先改，
  校验层跟着改。**登记在 §8，不留在注释里。**

### 3B.5 标识符：不得使用 BIC，理由与账号那条同源

**`AnyBIC` 在规范里带一条明确约束**，MDR Part 2 原文：
"Only a valid Business identifier code is allowed. Business identifier codes for financial or
non-financial institutions are **registered and published by the ISO 9362 Registration
Authority**"。

**合成机构没有注册过 BIC。填一个进去就是声称一个并不存在的注册标识**，
与 §3A.6 里 `AllocAcctIDSource` 不填 BIC/DTCC/OMGEO 是同一条理由，
**只是这一次规范把话说得更死**——那里是 CMOP 自律，这里是规范约束。

**因此参与方一律走专有标识分支：**

| 位置 | 取值 |
|---|---|
| `sese` 各参与方 | `PrtryId`，标识由根种子确定性派生，规则同 §6.3 |
| `pacs.009` 的 `Dbtr` / `Cdtr` | 同上，不填 `BICFI` |
| `camt` 的账户服务方 | 同上 |

**这条要作为断言存在，不是约定。** 生成器里任何一个 BIC 形状的字符串都是违规，
**而且它过得了 XSD**——`AnyBICIdentifier` 的正则只检查形状，不检查注册与否。
**这是又一条"schema 合法但违反规范"的检查**，归入
[验证与对账规范](validation-and-reconciliation-specification.md) 的 V1 与 C2 两级。

### 3B.6 与事实的绑定

**与 §3A.7、§6.5 同构：**

- 结算指令与状态回报的日期必须落在所引机构的存续区间内。
- **机构维度不建并户模型。** §3A.5 的并户是账户维度的真问题，**机构合并不在本阶段建模**，
  理由与 §3A.5 末段标的维度不建合并相同：**没有 BQ 需要它，而建了就要连带处理事实归属的
  转移**。**两个维度在这一点上再次不对称，不要相互类比。**

### 3B.7 结算方是一条有序链，不是五个独立槽位

**2026-09-12 补，起因是读了 `Party2PresenceRule` 一族**，见
[监管数据契约](regulatory-data-contracts.md) §4C.6.2。**这条修正了 §3B.1 的一个前提。**

§3B.1 说"角色不是实体"，按角色槽位取方。**槽位之间当时被默认成彼此独立的**，
可以各填各的。规范说不是：`Party2` 出现则 `Party1` 必须出现，`Party3` 出现则 `Party2`
必须出现，一直到 `Party5`。**结算方是一条从 1 号起连续的链，中间不得有洞。**

**生成顺序因此固定为两步，不能合成一步：**

1. **先抽这一笔用几层结算方**，记为 n。
2. **再从 `Party1` 到 `Partyn` 连续填**，`Partyn+1` 起一律空。

**先抽方、再看填哪个槽位的写法是错的**，它会产生 `Party1` 与 `Party3` 有值而 `Party2`
空着的报文，**每个方标识符各自都合法，整条报文违规**。

**n 的默认值取 2。** 规范的 `SettlementChainGuideline` 说 SMPG 建议至少三层：
存管机构、存管机构的参与者（`Party1`）、参与者的客户（`Party2`）。
**存管机构不占 `Party` 槽位**，所以"至少三层"对应到这里是 `Party1` 与 `Party2` 两个槽位。
**该指引是 Guideline 不是 Rule，不进校验层**，只用作默认值的出处。

**n 不随机变化。** 已冻结场景都是单一市场单一层级，**让 n 在 1 到 5 之间抖动只会
制造无人消费的多样性**，而链条深度的多样性要等到多市场场景才有意义。

## 4. 公司行为事件

### 4.1 一个必须先讲清的区别

**公司行为不是采样生成的，是回放的。** 一对一绑定意味着真实事件序列原样落到对应的合成标的
上。因此本节的实测分布**不是生成器的输入参数，而是回放正确性的校验目标**：生成结果的分布
若偏离这些数字，说明绑定或回放出了错。

采样只用于交易生命周期事实（§6），那里没有真实数据可回放。

### 4.3 四条已知的口径局限

1. **拆股与分红来自申报人自报**，不是交易所权威公告，因此是样本而非完备馈送。
2. **分红实测每年 1.69 次，低于按季分红应有的 4 次。** 说明该概念被大量申报人漏标。生成器
   不得把这个数字当作真实分红频率，只能当作"本数据集能观测到的频率"。
3. **`formerNames` 的日期字段不是更名生效日**，只有次数可用，见 §3 与
   [原始数据源清单](raw-data-source-inventory.md) §5.8。
4. **Form 25 按证券类别申报，不等于公司消亡。** 41.8% 中包含换所上市、认股权证类别退市等
   情形。把它直接当作公司死亡率会严重高估。

四条都必须写进对外口径。声称覆盖完备是本项目最容易被问倒的地方。

## 5. 脏数据契约

**脏数据分两类，来源必须始终可区分。**

| 类别 | 含义 | 现有样本 |
|---|---|---|
| 外生 | 来自真实数据本身的缺陷或口径差异 | 三例，见下 |
| 注入 | 生成器按契约主动制造 | 待定，见 §6 |

外生脏数据比注入脏数据更有说服力，因为它不是自己设计给自己解决的。已确认的外生样本：

- **拆股比例字段的方向歧义与异常值。** 1840 条中 183 条需裁决，含 43 条恰好等于 1 的空
  拆股、72 条大于 100 的疑似误标股数、1 条最大值达 1.1 亿。处理规则见
  [原始数据源清单](raw-data-source-inventory.md) §5.5。
- **两个官方汇率口径对同一天同一货币对给出不同数值**，构成口径性差异的天然样本，见
  同一文档 §5.1。
- **`formerNames` 的日期字段语义与直觉不符**，字段存在、格式正确、值却不是更名生效日。
  这类缺陷比空值和格式错误危险得多，因为它不触发任何校验，见
  [原始数据源清单](raw-data-source-inventory.md) §5.8。
- **加拿大央行在 2017 年更改了汇率发布方法**，十年序列必须拼接两段。拼接边界上的口径
  变更、重复与缺口是真实的参考数据不连续案例。**必须主动保留这个断点**，用单一序列绕过去
  等于丢掉一个免费的高价值用例。

**注入脏数据的清单待 FIX 证据到位后编写。** 每一类必须写明：注入位置、注入比例、检测手段、
以及正确处理后的预期结果。没有预期结果的注入不是测试，是噪声。

## 6. 交易生命周期事实

**范围限定为 L-1。** 契约已就位：字段与报文矩阵见
[监管与行业数据契约](regulatory-data-contracts.md) §3.3，条件必填的条件见 §3.3.1，状态转移
见 §3.4，逐步取值见 §3.5。撤单、改单、拒绝属 L-2 起的后续路径，本节不涉及。

### 6.1 采样字段与派生字段必须分开

**这是本节最重要的一条规则。** L-1 的每一步里，一部分字段是自由的，另一部分完全由前面的
成交序列决定。

| 类别 | 字段 |
|---|---|
| 采样 | `OrderQty`、成交笔数、各笔 `LastQty` 与 `LastPx`、`TransactTime` |
| 派生 | `CumQty`、`LeavesQty`、`AvgPx`、`OrdStatus`、`ExecType` |

**派生字段必须由生成器计算，绝不允许采样。** 采样它们的生成器会产出违反自身不变量的数据，
此后管道里出现的每一个差异都无法判断是管道的错还是数据的错，而区分这两者正是本项目的全部
价值所在。

`ExecType` 与 `OrdStatus` 由 L-1 的步骤位置唯一决定，见 §3.5 的逐步表，不存在选择空间。

### 6.2 分布参数：已定案

这五项是决策，不是证据问题。**没有任何公开数据能告诉我们合成订单该多大**，因为标的本身是
合成的。2026-09-09 采纳下表取值。

**必须诚实标注的一点：具体标量是任意的。** 有依据的是约束与分布形状的选择，中位数 500、
σ 取 1.5、±10 bp 这些数字没有证据支撑，它们只是满足约束的一组自洽取值。**不得在对外口径里
把它们说成"符合市场实际"。** 它们的用途是让生成器跑起来，Phase 1 实测行宽与压缩率后回调。

| 参数 | 取值 | 形状的理由 | 改动代价 |
|---|---|---|---|
| 每单成交笔数 | `3 + Geometric(p = 2/3)`，均值 3.5，截断于 12 | 与 §6.4 每单约 5.5 条报文自洽；几何分布给长尾且只需一个参数 | 低，只改行数 |
| `OrderQty` | 对数正态，中位数 500、σ = 1.5，上限 100000，吸附到 100 股整手，5% 留作零股 | 真实订单量在整百整千上高度聚集，纯连续分布会让下游按手计算的逻辑失去被检验的机会；5% 零股保证该分支被覆盖 | 低 |
| 数量拆分 | 按剩余量逐笔切分，每笔至少一手，末笔取精确余量 | 见下 | **高** |
| 各笔 `LastPx` | 以该单到达价为中心 ±10 bp 的随机游走，取自该标的的合成价格序列 | 见下 | **高** |
| `TransactTime` | 交易时段内指数间隔，均值 45 秒，链内严格递增 | 同一订单各笔成交相隔秒到分钟，不是均匀铺满全天 | 低 |

**其中两项互相牵动，改一个必须连带复核容量。** `OrderQty` 与每单成交笔数共同决定每标的
每交易日的行数，直接影响 §6.4 的推导，而 `OrderQty` 同时决定 Silver 的行宽。它们属于"改动
本身便宜、但会推翻容量估算"的类别，不是可以随手拧的旋钮。

两项高代价的说明：

**数量拆分不能用"先按比例切分再取整"。** 那种做法会在取整时产生零数量成交，或让合计对不上
`OrderQty`，而 `CumQty` 与 `LeavesQty` 是派生字段，一旦合计错位，§3.6 的条件式立刻失效，
生成器就产出了违反自身契约的数据。逐笔切分并让末笔承担余量可以保证合计恒等，代价是末笔的
数量分布与前几笔不同，这一点必须在文档里承认，不能假装各笔同分布。

**成交价必须与估值用的价格序列同源。** 若成交价单独随机生成，`AvgPx` 就与持仓估值所用的
价格无关，[验证与对账规范](validation-and-reconciliation-specification.md) §2.3 的 R1 会
产生一个恒定的、与管道无关的差异。届时对账永远不平，而且原因在数据里而不在管道里——正是本
项目最该避免的失败模式。

### 6.3 标识符必须由种子决定

`ClOrdID` 在订单内唯一，`ExecID` 全局唯一，`OrderID` 在接受回报时分配。

**三者都必须由根种子确定性派生，不得使用随机 UUID。** 随机标识符会让同种子重跑产出不同的
主键，§2 的可复现性契约随之失效，而且失效方式是静默的：数据看起来完全正常，只是再也对不上
上一次运行。

### 6.4 L-1 对数据量的影响

L-1 规定每单至少五条报文，一条新建、一条接受、至少三条成交。按每单约 5.5 条估算，配合
[工作负载基线](../workload-baseline.md) §1 的 20 至 50 亿行目标：

| 推导量 | 结果 |
|---|---|
| 订单总数 | 约 3.6 亿至 9.1 亿 |
| 每个标的每个交易日的订单数 | 约 12 至 29 |

**这个比例不能写进容量模型。** L-1 强制至少三笔成交，刻意排除了单笔全成，而真实市场里单笔
全成占很大比例。L-2 起引入这些路径后，每单报文数会下降，要达到同样的行数目标，订单数必须
相应上升。**把 L-1 的比例当成稳定参数，会在扩展场景时把容量估算整体推翻。**

### 6.5 与标的维度的绑定

订单与成交的 `TransactTime` 必须落在该合成标的的存续区间内，见 §3。上市之前与退市之后不得
存在任何事件。

成交量分布必须以标的生命周期为条件，且公司行为日前后应出现可观察的量能变化。这一条不依赖
FIX，属于业务常识而非协议细节。

### 6.6 目标行数在标的之间的分配：已定案

**定于 2026-09-12。** §8 此前把它登记为未决。它不是容量问题——总量区间已由
[工作负载基线](../workload-baseline.md) 给定——**它是分布形状问题**，
而形状决定下游哪些代码路径会被走到。

**均匀分配是错的，理由不是不真实，是它让整类问题消失。** 真实交易活跃度高度集中，
少数标的占绝大部分成交。均匀分配下：

- **分区大小全部相近**，倾斜分区、大分区的 compaction、小文件问题**一个都测不到**，
  而 W3 正是为这些而设。
- **Gold 聚合的长尾行为消失**，头部标的与尾部标的没有区别，
  **按标的下钻的查询代价变成常数**，那与真实系统的形状完全不同。

**契约：按秩次的幂律分配，形状参数与下限如下。**

| 参数 | 取值 | 理由 |
|---|---|---|
| 形状 | 齐普夫型，指数 **1.0** | 指数 1 给出"第 n 名的量约为第一名的 1/n"这一经典形状，**是一个可以被说清的选择**，而不是拟合出来的数 |
| 秩次来源 | **由根种子确定性派生，与标的代码无关** | 秩次若跟代码顺序走，头部标的会聚在代码空间一端，**分区裁剪的效果会被高估** |
| 每标的下限 | 十年窗口内 **至少 1 个交易日有事实** | 见下 |
| 零事实标的 | **显式保留一批，约 5%** | 见下 |

**下限与零事实这两条看着矛盾，实际分工不同。**

**保留约 5% 的零事实标的是有意的。** 维度里有、事实里没有的标的，
**是外连接、维度覆盖率统计与"孤儿维度行"这一类问题的唯一输入**。
把每个标的都塞进事实表，这类问题在测试里就不存在了，**而它在真实系统里天天存在**。

**其余 95% 保底至少一天有事实**，是为了让幂律的尾部不退化成"一大批完全相同的空标的"——
那样尾部就没有形状了，**只剩一个零点**。

**与公司行为的交互必须显式处理。** 实测 7294 个标的有事件、12505 个是全集。
**活跃度秩次与"是否有公司行为"两者独立采样**，因此会出现头部标的没有任何公司行为、
尾部标的却有反向合股这两种组合。**两种都要保留**：

- **头部无事件**的标的用于证明重述逻辑不会误触发。
- **尾部有事件**的标的是最难的一类：**行数少，重述却要走全套路径**，
  而这正是 §7 第 3 条不变量在小样本上最容易被舍入误差压垮的地方。

**总量落点由这条分配加 §6.2 的每单参数共同决定**，两者任意一个改动都要重算总量，
**与 §6.2 末段记的牵动关系是同一条**。

## 6A. 更名事件：不追求真实日期，且锚定到公司行为

**决定一：生成器不需要准确的更名日期，因此不从申报文件中恢复。**

理由与价格同源。标的是合成的，绑定的真实更名事件只提供**计数与次序**，日期本身不携带可被
检验的信息。[原始数据源清单](raw-data-source-inventory.md) §5.8 已确认 EDGAR 的
`formerNames` 区间是名称出现窗口而非法定变更日，且区间衔接率仅 2.6%、重叠率 27.4%。
**从申报文件恢复真实日期是一项独立工作，收益为零**：合成标的上的"真实日期"并不比合成日期
更真。

保留的是有信息量的部分：49.0% 的标的有过更名、平均 1.58 次、最多 10 次、每标的每年 0.0772
次，是拆股率的五倍多。这些计数决定维度版本链的长度分布，**那才是要被检验的东西**。

**决定二：更名时点锚定到公司行为，不在存续区间内均匀分布。**

均匀分布更容易实现，检验强度却更低。锚定分布能同时制造两类被测场景：

1. **同一标的的多个维度事件在时间上聚集**，于是 SCD Type 2 的版本链出现短区间与同日多次
   变更，而这正是"区间不重叠、不留空隙"那条不变量最容易被破坏的地方，见 §7 第 2 条。
2. **更名与反向合股同期发生。** [原始数据源清单](raw-data-source-inventory.md) §5.7 实测
   29.0% 的反向合股申报人后来退市，说明这类事件本就在困境期聚集。让更名跟随该聚集，重述与
   维度变更就落在同一批次里，**而这是最难对的一种账**。

**契约**：每次更名以该标的存续区间内的某个公司行为为锚点，落在锚点的近邻窗口内；无公司行为
可锚定时，才退回该区间内均匀取样。窗口宽度与锚定比例**已于 2026-09-12 定案，见 §6A.1**。
它们决定检验难度而非正确性，**但检验难度定不下来，注入清单就没有已知命中率**。

### 6A.1 锚定窗口与锚定比例：已定案

**定于 2026-09-12。** §6A 把这两项推到 §8，理由是它们决定检验难度而非正确性。
**该理由成立，但不构成不定的理由**：检验难度定不下来，注入清单就没有已知的命中率，
§6.3 那套档位也就无处落地。

**必须先说清一件事：窗口以营业日计，不以日历日计。** 批次按营业日跑，
**日历日窗口会把一部分事件丢到周末**，而周末没有批次，它们会被静默顺延到周一，
**人为抬高同日率**。抬高的幅度取决于窗口宽度与星期分布，**是一个既说不清又改不掉的偏差**。
以营业日计就没有这个问题。

| 参数 | 取值 | 理由 |
|---|---|---|
| 锚定比例 | **70%** | 留 30% 退回均匀取样，**保证长区间与孤立变更仍有样本**。全部锚定会让版本链清一色是短区间，反而测不出正常情形 |
| 窗口形状 | 离散，取值 {0, ±1, ±2, ±3, ±5} 营业日 | 见下 |
| 同日权重 | **占已锚定事件的 25%** | 同日多次变更是 §7 第 2 条最容易失效的输入 |
| 其余权重 | ±1 各 15%、±2 各 10%、±3 各 7.5%、±5 各 5% | 随距离递减，**但不趋零**，五个营业日外仍有样本 |

**三档权重各自守一类被测场景，不是一条平滑曲线的离散化：**

1. **0 天，占已锚定的四分之一。** 同一标的同日发生公司行为与更名，
   **版本链上出现零长区间或同日两个版本**，这是"区间不重叠不留空隙"最容易被破坏的输入。
2. **±1 与 ±2，合计占一半。** 事件落在相邻批次，
   **重述与维度变更跨批次交错**，这是 §6A 决定二真正想要的那类难账。
3. **±3 与 ±5，占四分之一。** 事件在同一周内但不相邻，
   **用于证明短区间的处理没有被写死成"只认同日与隔日"**。

**取值范围止于 ±5 营业日，即一个自然周。** 再宽就与均匀取样没有区别，
**而均匀取样已经由那 30% 承担**，两者重复没有意义。

#### 越界时重采样，不裁剪

锚点近旁的窗口可能越出标的存续区间。**裁剪到边界是错的**：
它会让事件在存续区间的首末日堆积，**制造一个纯属实现产物的尖峰**，
而下游分析看到的是"上市首日与退市当日更名特别多"这样一个假规律。

**契约：越界则在同一分布上重采样，连续三次仍越界则该次事件退回均匀取样。**
三次是任意值，**但"有限次后退回"这条不是**——不设上限的重采样在极短存续区间上不终止。

**退回的那部分要计入 30% 之外单独统计。** 否则实际锚定比例会低于 70% 而无人知道，
**这类静默偏移与 §6A 拒绝日历日窗口是同一种毛病**。

## 6B. 已冻结场景的取样参数：已定案

**九条场景已于 2026-09-12 冻结**：A-2、A-3、C-2、C-3，见
[监管与行业数据契约](regulatory-data-contracts.md) §3A.10 至 §3A.14；
资金段的 P-5、P-5a 与 P-5b 见同一文件 §4B.12、§4B.13 与 §4B.14；
公司行为段的 S-7a 与 S-7c 见 §4D.10 与 §4D.11。
**契约说的是每条场景长什么样，本节说的是它们各占多少。**

**先说为什么现在就要定。** 与 §6A.1 同一个理由：
**场景占比定不下来，注入清单就没有基线**。
[验证与对账规范](validation-and-reconciliation-specification.md) §6.3 把注入分成"稀"与"中"两档，
**而这两档量的是相对于正常数据的比例**。若 A-2 占分配链的 15%，
"同一账户两条确认"就是常态而不是异常，**那条注入随之失去意义**。

### 6B.1 场景必须互斥取样，不能各自独立开关

**这一条是本节唯一一条不是任意标量的规则，它由契约推出来。**

A-6 与 C-5 是被显式推迟的组合场景（契约 §3A.13、§3A.14），
推迟的理由是**重述路径与更正路径从下游看长得一样，各自会掩盖对方的失效**。

**若生成器把 A-2 与 A-3 做成两个独立的伯努利开关**，占比分别为 p 与 q，
**那么 A-6 会以 pq 的概率自己出现**。取 p = q = 0.1 就是 1%，
**在百万级链条上是上万条，足够把两条校验的失效同时掩盖掉，而且没有人做过这个决定**。

**契约：每条分配链从一个互斥的分类分布中取一个场景，不设独立开关。**
组合场景要出现，必须显式加进这个分布，**而不是作为两个开关的乘积悄悄出现**。

**这类"两个合理的局部决定相乘出一个没人做过的全局决定"是本项目最难查的一类错误**，
与 §6A.1 拒绝日历日窗口是同一种毛病：**偏差是实现产物，且每一步单独看都对**。

### 6B.2 分配链的场景分布

**标量全部是任意值，与 §6.2 同性质，不得对外说成"符合市场实际"。**
有依据的是互斥取样（§6B.1）与各档要守的场景，不是数字本身。

| 场景 | 占比 | 这一档守什么 |
|---|---|---|
| A-1 一次通过 | **80%** | 正常路径必须占绝大多数，**否则异常处理反而成了主流程** |
| A-2 账户层拒绝后 Replace | **8%** | 版本链深度 1，链式回溯校验的第一个用例 |
| A-3 迟到，落入次日批次 | **10%** | 重述与双版本保留的唯一输入，**主 BO 的验收判据挂在这里** |
| A-4 数量对不上 | **2%** | 属注入而非正常路径，见验证与对账规范 §6.3 |

**A-3 取 10% 而不是更低，理由是它必须在每个批次里都出现。** 若占比过低，
大量批次中没有任何待重述的结果，**重述路径在多数批次里不被执行**，
而不被执行的路径与不存在的路径在测试上等价。

**A-3 也不能更高。** 主业务流的设定是分析员到岗时队列里有异常，
**队列是异常不是常态**；占比过高会让"沿链定位最大一条差异"这个动作失去意义。

### 6B.3 确认链的场景分布

**确认是逐账户的**，一条分配链下有 N 个账户，**场景在账户层取样而不是在链层**。

| 场景 | 占比（按账户） | 这一档守什么 |
|---|---|---|
| C-1 一次通过 | **85%** | 同上 |
| C-2 被拒后 Replace | **7%** | **打掉"每账户恰好一条确认"**，见验证与对账规范 VC-2 |
| C-3 迟到，跨越结算日 | **8%** | 停留时长这一新检查形状的唯一输入，**且它接到 S-2 上** |

**C-3 的 8% 有一个下游后果，必须一起看：它决定 S-2 的输入量。**
契约 §3A.14 让 C-3 落到已冻结的 S-2 上，**于是确认段的这个占比会通过链条传到结算段**。
**改这个数就是改 S-2 的样本量**，不是一个局部旋钮。

### 6B.4 迟到偏移：按营业日，形状照 §6A.1

**理由与 §6A.1 完全相同，不再重复论证**：批次按营业日跑，
日历日偏移会把事件静默顺延到周一。**契约 §3A.13 另有一条独立理由**：
分配指令上唯一必填的时间信息是 `TradeDate`，是日期不是时刻，
**按天量不是选择，是唯一可行的量法**。

| 场景 | 偏移取值 | 权重 |
|---|---|---|
| A-3 | +1 营业日 | 75% |
| A-3 | +2 营业日 | 20% |
| A-3 | +3 营业日 | 5% |
| C-3 | +1 营业日 | 30% |
| C-3 | +2 营业日 | 50% |
| C-3 | +3 营业日 | 20% |

**A-3 与 C-3 的分布形状故意不同。**
A-3 压在 +1 上，因为主业务流讲的就是"T+1 早晨"；
**C-3 压在 +2 上，因为 C-3 的定义是跨越结算日，而结算日是 T+1**，
偏移 +1 未必跨得过去，**取决于确认在 T 日的哪个时刻发出**。

**这就是那条"停留时长按秒记、跨界判定按营业日做"的口径在生成侧的对应物**
（契约 §3A.14）。**生成器必须先定发出时刻，再判是否跨界，不能反过来**：
先决定"要跨界"再倒推时刻，会让停留时长的分布出现一个纯属实现产物的下界。

### 6B.5 资金段的入账状态分布

**这一项与前三项不同：它不是场景开关，是每一笔资金各自的属性。**
出处见[监管数据契约](regulatory-data-contracts.md) §4B.12。

| 当日终态 | 占比 | 说明 |
|---|---|---|
| 只出现在 `camt.053`，`BOOK` | ~~70%~~ **64%** | 不生成日内报告，P-4 的原样。**已于同日改，见 §6B.5a** |
| 先在 `camt.052` 里 `PDNG`，再在 `camt.053` 里 `BOOK` | **26%** | P-5 |
| 先在 `camt.052` 里 `PDNG`，被 `RJCT`，**对账单里没有** | **4%** | P-5a，见契约 §4B.13 |

**后两行必须互斥取样，不能各开一个开关**，理由同 §6B.1。
**P-5a 的 4% 同样高于真实市场**：它的六条不变量里有四条只在被拒时才有数据。

~~**`FUTR` 一律不生成。**~~ **已于同日冻结为 P-5b，占 6%，见 §6B.5a。**
**本表四行合起来是 100%，改任一行都要连带改另外三行。**

**余额类型的生成口径，2026-09-12 补记，出处见契约 §4B.15：**

1. **每份 `camt.053` 带 `OPBD`、`CLBD` 与 `PRCD` 三条。** `PRCD` 规范上可选，
   **生成它是为了让缺一天的对账单能被下一份报文自己指出来**。
2. **每份带 `PDNG` 明细的 `camt.052` 带 `ITBD` 与 `XPCD` 各一条。**
   两者之差即当日未入账金额，**与内部账构成两条独立算路**。
3. **笔级状态回报一律不用 `ACSC`，结算完成用 `ACCC`。**
   `ACSC` 的码值定义自带"不得当作财务信息、须有双边协议"两条限制，**它只作注入**。
4. **对账单按营业日连续生成，不得跳日。** 缺日只作注入，否则跨日等式会在正常数据上误报。

**两条硬约束，任何取值下都必须成立：**

1. **`camt.053` 里 `PDNG` 的占比恒为 0。** 不是取样得到的 0，是生成器不产生这个组合。
   规范的 scope 禁止它，**而 31 条约束一条都不管**，所以只能在生成侧堵。
2. **走 P-5 的每一笔，从 `Ntry` 到 `Refs/EndToEndId` 五层必须全给。**
   规范一层都不要求（见契约 §4B.12 的基数表），**少给一层数据仍然合法，
   但 C4-17 就再也判不了**。

**预计入账日的偏移单独取样**，形状照 §6A.1，集中在 +0：

| 第 2 步预计入账日与第 4 步实际入账日之差 | 占比 |
|---|---|
| 0 个营业日 | 80% |
| +1 个营业日 | 15% |
| -1 个营业日 | 5% |

**这个偏移不是错误，是预测误差**，C4-20 明令不得把它判成违规。
**它取 0 的占比不能设成 100%**，否则 C4-20 这条否定式断言永远没有被测数据，
**等于没写**。

### 6B.5a 起息日晚于入账日的分布

**出处见[监管数据契约](regulatory-data-contracts.md) §4B.14。**
**取样单位与 §6B.5 相同，是一笔支付**，两节的占比合起来必须是 100%。

§6B.5 的三档（`BOOK` 直入 70%、P-5 的 26%、P-5a 的 4%）**改为四档**：

| 终态 | 占比 |
|---|---|
| 当日 `BOOK` 直接入账 | **64%** |
| P-5：先 `PDNG` 后 `BOOK` | 26% |
| P-5a：先 `PDNG` 后被拒 | 4% |
| **P-5b：`FUTR`，起息日为 D+2** | **6%** |

**六个百分点全部从 `BOOK` 直入那一档划出**，P-5 与 P-5a 不动。
理由是那两档的占比已经按各自判据的取数需要定过一轮，**再动会连带重算注入的稀／中分档**。

**四条硬约束：**

1. **起息日固定为 D+2，不做分布。** 本场景要证明的是跨日这件事本身，
   **把间隔摊成一个分布只会让 C4-33 的样本落在不同日期上，不会多验证任何一条判据**。
2. **`INFO` 一条都不生成。** 三方对账的任何一方都挂不上它（契约 §4B.14.6）。
   **它只作注入。**
3. **`FUTR` 与 `PDNG` 不得出现在同一笔支付的生命周期里。**
   两者不在一个维度上（契约 §4B.14.2），**混着生成会让 C4-20 与 C4-32 同时可触发**，
   而这两条对 `BookgDt` 的要求正好相反。
4. **含 `FUTR` 的日子必须同时存在不含 `FUTR` 的日子。**
   C4-34 是 C4-8 的限定版，**两条都需要被测数据**，
   而"当日无 `FUTR`"是原式唯一的取数来源。

**6% 明显高于真实市场的远期起息占比。** 理由与 §6B.6 的冲正率相同：
**P-5b 的七条不变量里有五条只在 `FUTR` 出现时才有数据。**

### 6B.6 公司行为过账与冲正的分布

**出处见[监管数据契约](regulatory-data-contracts.md) §4D.10。**
**取样单位是"一个公司行为事件在一个账户上的一次过账"，不是事件。**

| 终态 | 占比 |
|---|---|
| 只有 `seev.036` 过账确认 | **94%** |
| `seev.036` 之后有一条 `seev.037` 过账冲正（S-7a） | **6%** |

**三条硬约束：**

1. **`seev.036/MvmntConfId` 一律生成**，规范是 0..1，只有分页时才强制。
   **不生成的情形只作注入**，见[验证与对账规范](validation-and-reconciliation-specification.md) §6.4A。
2. **冲正原因码固定取 `IPRI`。** 九个值里只有两个说得通，另一个是 `OTHR`（契约 §4D.10）。
   **不做原因码分布**：这一段的原因分析价值为零，把样本摊薄到九个值上没有意义。
3. **事件撤销（`seev.039`）一条都不生成。** S-7b 未冻结，
   **而误生成它会让 E-2 与 E-9 同时有数据，两条判据互相掩盖**。

**冲正率 6% 明显高于真实市场。** 这是有意的：**S-7a 的判据有六条，
其中三条（S7a-4、S7a-5、S7a-6）只有在冲正发生时才有被测数据**。
**按真实概率取样会让这三条长期处于"从未验证"状态**，
而"没有故障注入的断言等于从未验证过"是本项目的既有口径。

### 6B.6a 公司行为引发的撤销并重发的分布

**出处见[监管数据契约](regulatory-data-contracts.md) §4D.11。**
**取样单位是"一条已发出但尚未结算的结算指令"**，不是事件、也不是账户。

| 终态 | 占比 |
|---|---|
| 不受任何公司行为影响 | **97%** |
| `CANT` 撤销并重发（S-7c） | **2%** |
| `CORP` 撤销且无重发 | **1%** |

**`CANT` 与 `CORP` 必须同时生成，比例定死在 2:1。**
两者的差别只有"并重发"三个字，**而对账口径正好相反**：
`CORP` 之下该笔消失是对的，`CANT` 之下该笔消失是漏了一条。
**只生成其中一种，E-16 与 E-17 里必有一条永远没有反例**，
于是"撤销之后总会有重发"或"撤销之后从不重发"两种错误口径各有一种查不出来。

**四条硬约束：**

1. **重发指令一律带 `Lnkgs`，`Ref` 走 `SctiesSttlmTxId`，`PrcgPos/Cd` 取 `INFO`。**
   规范里这三处全是可选或多选，**其余写法只作注入**。
2. **`PrcgPos` 取 `WITH` 的数据一条都不进正常样本。** 按 C80，
   它会让重发指令永久挂起（契约 §4D.11.4）。**这条数据完全合规**，
   所以它必须只出现在注入里，否则会污染结算及时率。
3. **撤销与重发的 `CorpActnEvtId` 对照表由生成器直接落表**，
   不试图从报文里推。**报文层面没有这个字段**，S7c-5 靠这张表核。
4. **`SCEX` 一条都不生成。** 它的定义里带一句 should 级的选码指引，
   要求公司行为相关的撤销改用 `CORP`。**生成它只会制造一条与指引冲突的样本**，
   而 should 不是 must，**判据无法把它判成违规，也无法判成合规**。

**总占比 3% 是按"能产生判据数据"倒推的，不是按市场频率。**
S-7c 有七条不变量，**其中五条只在撤销发生时才有被测数据**。

### 6B.7 六项与既有参数的牵动关系

**改任一项都要连带复核，与 §6.2 那两项高代价参数同类。**

1. **A-2 与 C-2 的占比抬高报文条数。** A-2 一条链从 3 条报文变 6 条，
   C-2 一个账户从 3 条变 6 条。**§6.4 的每单报文数推导要重算**，
   而那个数直接进容量估算。
2. **C-3 的占比决定 S-2 的样本量**，见 §6B.3。
3. **A-3 的占比决定每批次待重述结果的条数**，进而决定
   Silver 合并链的写放大。**该机制尚未定案**，登记在 §8。
4. **P-5 的占比抬高的是资金段报文条数，且抬两次**：一笔多出一条 `camt.052`，
   而这条报文里还要逐笔回显 `TxDtls`。**§6.4 的推导同样要重算。**
5. **S-7c 的占比落在结算指令上，而不是落在公司行为事件上。**
   **它是唯一一个取样单位在结算段、起因在公司行为段的场景。**
   公司行为事件数一改，S-7c 的绝对条数不变；**结算指令数一改，它才变**。
   **这一条最容易被算错**，因为它写在公司行为的小节里。
6. **S-7a 的占比与公司行为事件数相乘，不是相加。** 取样单位是"事件乘账户"，
   **所以受影响账户多的事件会成比例放大冲正条数**。§7 的公司行为回放规模一改，
   这个数就要重算。

**六条牵动关系有一个共同点：被牵动的都不在本节。**
所以这几个数不能在本节内部单独调，**每次改都要走一遍上面六条**。

## 7. 业务不变量

不依赖 FIX、由标的维度与公司行为决定的三条：

1. 上市之前与退市之后不存在成交。
2. 标的维度的版本链在任一时点有且只有一个当前版本，区间不重叠、不留空隙。
3. 公司行为回放后，受影响标的的持仓数量与成本基础按调整因子 F 变换，数量乘 F、成本基础
   除以 F，且账户层面的总成本基础不变。

第 3 条是重述正确性的核心断言，也是反向合股最容易出错的地方。**它在写下时就引用了"账户
层面"，而当时账户维度并不存在**，见 §3A。该条现在有了依托，但**求值方式必须按 §3A.5 改成
在并户链闭包上求和**，逐账户求值会把正常的并户报成违反。

账户维度带来的三条，与上面三条同级：

4. 开立之前与关闭之后不存在分配；并户之后不得再向被并入方分配。
5. 账户与客户两条版本链各自在任一时点有且只有一个当前版本，区间不重叠、不留空隙。
6. 同一笔分配的各账户同属一个客户。

**第 6 条不会被任何 FIX 校验发现**，因为 FIX 不知道账户归谁，见 §3A.2。

依赖 FIX 字段的三条已核对完毕，见[监管与行业数据契约](regulatory-data-contracts.md) §3.6。

**其中第一条已确认是条件式，不是不变量。** `CumQty` 加 `LeavesQty` 等于 `OrderQty` 只在
L-1 的 New、Partially Filled 与 Filled 回报上成立，不得推广到 Canceled、Expired、Rejected
等终止状态。生成器在 L-2 起引入这些状态时，必须同步修改断言，**不能沿用 L-1 的写法**。

另两条中，持仓累加与均价自洽都标注为 CMOP 业务推导而非 FIX 显式不变量。这个区分要保留到
对外口径里：能说清哪些来自规范、哪些是自己推的，比两者都说成"符合 FIX"更经得起追问。
