# Postmortems

Postmortem 记录已经造成实际影响的事故，目标是解释影响、根因、为何没有更早发现，以及
怎样防止同类问题再次发生。它不是普通调试日志。

## 触发条件

出现以下任一情况时必须评估并通常建立 postmortem：

- 数据永久丢失、出现无法回补的缺口，或恢复成本显著。
- 错误数据、指标、监管结果或风险结论已经被下游读取。
- 服务中断、数据管道失约或安全、隐私、合规边界被突破。
- 同类故障重复发生，说明既有防线或改进项无效。
- 事故虽被恢复，但暴露了可能造成重大影响的系统性缺陷。

开发期发现且未造成影响的问题不写 postmortem；上线过程中发现并当场解决的问题进入
对应 launch record。一次性手误或环境噪声留在 issue，除非它揭示了可重复的系统问题。

## 写作与生命周期

每篇至少包含 Impact、Timeline、Root cause、Why detection failed 和 Corrective actions。
对事不对人；改进项必须落到 PR、issue、ADR、监控或自动化门禁，而不是“以后注意”。

复盘完成后正文冻结。根因后来被新证据推翻时追加带日期的更正；决策因此改变时另写 ADR。
文件名使用 `YYYY-MM-DD-kebab-case-incident.md`。
