# Workload Baseline

> **Status**: Draft · **Date**: 2026-09-09
>
> 本文覆盖容量（§1 至 §4）与容量之外的工作负载包络（§5）。
>
> 当前数字是规划假设，不是实测基线。Phase 1 后必须用生成器和真实文件测量结果替换。

## 1. 目标规模

项目目标总量为 **800 GB–1.5 TB**。这个区间的目的，是让分区裁剪、小文件、增量处理、
shuffle spill、批次恢复和容量治理变成实际约束。

| 数据集 | 来源 | 当前规模假设 |
|---|---|---|
| orders / trades | 合成 | 400–700 GB，约 20–50 亿行 |
| positions snapshots | 由流水推导 | 100–200 GB |
| customer / account master | 合成 | 小于 1 GB |
| security master / corporate actions | 真实公开数据（SEC 结构化接口、GLEIF） | 数百 MB，其中 SEC 抽取实测 6 MB |
| daily market data | **合成**，见来源清单 §5.4 | 1–3 GB |
| SEC EDGAR XBRL | 真实公开数据 | 20–50 GB（**Later，可整体舍弃**，见下） |
| FX / interest-rate curves | 真实公开数据 | 小于 1 GB |

标的数量不再是自由参数。公司行为采用一对一别名绑定后，标的宇宙等于十年窗口内的真实申报人
集合。四十个季度全量抽取实测为 **12505 个**，其中 7294 个在十年窗口内至少发生过一次公司
行为。按目标成交量摊平后每个标的每个交易日几十到两百笔，该密度直接约束标的维度上的分区
与文件大小设计，见[原始数据源清单](requirements/raw-data-source-inventory.md) §5.6 与 §5.7。

这些数字尚未闭合到 800 GB–1.5 TB 的完整层级放大模型。Bronze/Silver 重复、Iceberg
metadata、snapshot、删除文件和 Gold 都需要在原始数据估算之外单独计算。

SEC EDGAR XBRL 不服务于暂定主 BO 的交易生命周期对账，其半结构化解析价值已由 FIX 与
ISO 20022 报文覆盖。它排在最后阶段，时间不足时整体舍弃，且不得进入任何前置阶段的
依赖链。

**这一条只针对批量解析财报 XBRL 这类工作负载。** 通过 SEC 的 `frames` 与 `submissions`
接口针对性抽取公司行为，体量在数十 MB 量级，角色是维度与参考数据而非 Bronze 事实，
不受本条约束，见[原始数据源清单](requirements/raw-data-source-inventory.md) §5.3。

## 1.1 日增量规模

按十年历史、每年 250 个交易日摊平：

| 数据集 | 全量假设 | 摊到单个交易日 |
|---|---|---|
| 交易生命周期事件 | 400–700 GB | 约 160–280 MB |
| 持仓快照 | 100–200 GB | 约 40–80 MB |
| 合计 | | **约 200–360 MB** |

日增量约为目标总量的万分之四。这个结论支撑
[平台架构](platform-architecture.md) §4.1：常驻日增量可以在 NAS 上执行，MBP 只承担
首次回填、全量重算和 compaction。

该摊平假设默认批次间分布大致均匀。真实的日内与季节性波动会产生峰值批次，峰值倍数需要
在 Phase 1 用生成器实测，不能沿用平均值做容量承诺。

## 2. 为什么不更小或更大

| 规模 | 工程含义 |
|---|---|
| 小于 10 GB | 单机 dataframe 工具即可完成，许多湖仓设计无法被真实检验 |
| 约 100 GB | 开始需要认真处理分区与列裁剪，但错误设计仍可能被硬件掩盖 |
| 500 GB–2 TB | 分区、小文件、增量、spill 和重跑成本开始形成明确反馈 |
| 大于 10 TB | 在当前目标下主要增加时间、硬件和费用，不明显增加新的工程问题 |

## 3. 存储预算

### NAS

- 物理容量：8 TB 起步，可扩展。
- 主要内容：Bronze、Silver、Iceberg metadata、snapshot 和必要备份。
- 8 TB 是容量上限，不是可用预算；必须预留 compaction、重述和恢复操作空间。

### OCI

- 本地盘：200 GB。
- Gold 初始预算：**40 GB**。
- Gold 预期远小于 Silver。超过 40 GB 时，首先检查是否混入明细粒度、snapshot 保留失控
  或表设计重复，而不是直接提高预算。
- **已挂号的例外一项：异常解释表。** 它是明细粒度的，由
  [平台架构](platform-architecture.md) §5.1 的下钻边界决定所要求。其行数由异常条数而非
  事实条数决定，量级远小于事实表，但必须单独监控行数、字节数与增长率，不得并入 Gold
  总量后失去可见性。
- 现有磁盘清理曾估算可回收约 60–70 GB，但该数字来自规划期环境盘点，CMOP 使用前必须
  重新测量，不能视为已承诺容量。

## 4. Phase 1 必测指标

| 指标 | 用途 |
|---|---|
| 各事件类型原始 bytes/row | 从目标行数推导生成量 |
| Parquet 压缩后 bytes/row | 推导 Bronze/Silver 实际容量 |
| 每个 partition 的文件数与中位文件大小 | 判断小文件和 compaction 需求 |
| Iceberg manifest 与 metadata 增长 | 估算规划开销 |
| Snapshot 与删除文件增长率 | 制定保留和过期策略 |
| Spark shuffle read/write、spill 与峰值本地盘 | 验证 MBP NVMe 容量 |
| Silver → Gold 输出比例 | 验证跨隧道 Gold 写入和 40 GB 预算 |
| 单个日增量批次的行数、字节数与峰值倍数 | 验证 NAS 常驻增量的可行性与内存分配 |
| 各关键批次运行时间与峰值内存 | 验证按需计算和 OCI 常驻预算 |
| 夜间批次端到端墙钟时间 | 验证 §5.2 的 07:00 截止时点是否可达 |
| 家庭上行带宽 | 估算首次回填推送 Gold 的耗时，见 §5.7 |
| snapshot 数量、标签数量与元数据体积 | 验证 §5.5 的打标签保留方案的开销 |
| 全量回填墙钟时间 | 它就是合成事实数据的 RTO，见 §5.6 |

每个数字必须记录测量日期、生成器版本或数据提交、Spark/Iceberg/Parquet 配置，以及运行
节点。没有这组上下文的压缩比和吞吐量不能进入容量决策。

## 5. 工作负载包络

容量只是包络的一个维度。以下七项与容量同等重要，缺任何一项都无法判断设计是否成立。
除非标注为实测，本节数字均为**规划假设**，Phase 1 必须用实测替换。

### 5.1 到达速率与批次节奏

| 场景 | 体量 | 执行端 | 频率 |
|---|---|---|---|
| 首次回填 | 800 GB–1.5 TB | MBP | 一次 |
| 日常增量 | 200–360 MB | NAS 常驻 | 每交易日 |
| 流式 demo | 窄窗口回放 | OCI | 按需 |

**回填与日常增量相差约四千倍。** 这个不对称是 MBP 与 NAS 分工的成因，不是硬件凑合的
结果。任何把两者放在同一节点上的方案，都会被其中一端的需求拖垮。

峰值倍数未知。日内与季节性波动会产生峰值批次，摊平后的平均值不能作为容量承诺，见 §1.1。

### 5.2 新鲜度目标

**唯一的硬截止时点来自关键业务流程**：分析员到岗时异常队列必须已经存在，见
[业务目标](requirements/business-objectives.md) §3.1。批次窗口是收市之后到次日营业开始
之前，目标为**次日 07:00 前完成**。这是所有其他指标的上位约束：任何设计若使批次跑不进
这个窗口，无论其他指标多好都不成立。

第二条：**更正报文必须在它到达的那个批次内完成重述**，不能推到下一批。T+1 只有一天窗口，
推一批就等于错过。

**新鲜度不是越新越好。** Gold 在批次之间不更新是设计选择，不是能力不足。分析员看到的是一
个确定的批次快照，而不是漂移的实时视图；差异归因需要一个稳定的比较基准，实时刷新反而会
让"这条差异是否已解决"失去确定答案。

### 5.3 访问模式

| 路径 | 发起端 | 形态 | 预期延迟 |
|---|---|---|---|
| Gold 固定报表与异常队列 | OCI Trino | 有界聚合与主键查找 | 秒级 |
| 异常解释链 | OCI Trino | 读已物化的 Gold 表 | 秒级 |
| Silver 宽扫描 EDA 与 Gold 重建 | 局域网 Spark | 全表或多分区扫描 | 分钟到小时 |
| Silver 逐笔排查 | 局域网 | 带强谓词 | 分钟级，仅工程用途 |

**对外路径不产生任何 Silver 访问**，见[平台架构](platform-architecture.md) §5.1。因此访问
模式的分布是**双峰的**，不是连续谱：要么是 Gold 上的小查询，要么是局域网上的大扫描。中间
地带被刻意清空，这正是隧道两端职责能够干净切分的原因。

### 5.4 并发

目标不是高并发。真实使用者是个位数的运营团队，设计目标为 Gold 上 1 到 5 个并发读。

**真正的并发风险在写入侧，不在查询侧。** 日增量的 `MERGE INTO` 与 compaction 若落在同一
分区，Iceberg 的乐观并发控制会产生提交冲突并触发重试。因此 compaction 必须与增量写入错开
排期，**不能靠重试兜底**：重试会把冲突从设计问题变成偶发的运行故障，而后者更难归因。

同一业务日的批次不允许重叠运行。重跑前必须确认前一次已终止，否则两次 `MERGE` 会互相覆盖。

### 5.5 保留策略

| 层 | 保留 | 依据 |
|---|---|---|
| Bronze | 十年全量，不可变 | 逐笔追溯的终点必须一直存在 |
| Silver | 十年全量 | 重述需要读回历史明细 |
| Gold | 十年 | 体量小，不构成约束 |
| Iceberg snapshot | 需明确过期策略 | 见下 |

**关键约束：snapshot 的保留窗口必须覆盖重述比较的需要。** 验收要求保留重述前后两个可比较
的版本；若 snapshot 先过期，该能力随之消失，而失效方式是静默的。

做法是**给每个业务日批次结束时的 snapshot 打标签**，让它独立于按时间的过期策略存活，而不是
简单延长所有 snapshot 的保留期。后者会让规划元数据无限膨胀，正是 §3 要避免的。

### 5.6 恢复目标

**本项目的资产不同质，RPO 与 RTO 必须分开谈。**

| 资产 | 可否重建 | RPO | RTO |
|---|---|---|---|
| 合成事实数据 | 可以，由种子与生成器完全决定 | 实际为零 | 等于回填时间，待实测 |
| 参考数据与别名映射表 | **不可以** | git 提交粒度 | 分钟级 |
| Iceberg 元数据与 snapshot | 部分 | 与对象存储备份同步 | 待定 |

参考数据不可重建的原因见[原始数据源清单](requirements/raw-data-source-inventory.md) §5.7：
证监会数据随补充申报变化，今天重跑得不到同一批数字。别名映射表一旦丢失，历史事件与合成
标的的对应关系就断了，已产出的结果再也无法解释。

**这两项是全项目唯一真正不可替代的资产。** 它们进 git 不只是为了可复核，也是备份手段。相
对地，占据几乎全部体量的合成事实数据反而是最容易恢复的，因为它由种子决定。

单台 NAS 不构成数据保护。对象存储仍需独立备份与恢复演练。

### 5.7 网络上限

| 链路 | 承载 | 估算 |
|---|---|---|
| 家庭局域网，千兆 | Bronze 与 Silver 的全部读写 | TB 级 |
| 隧道，日常 | 作业控制、元数据、Gold 增量 | 40 GB 摊到 2500 个交易日，约每批 16 MB |
| 隧道，回填 | 首次 Gold 全量推送 | 一次性 40 GB |

**日常隧道负载可以忽略**，这从数量上验证了架构的分工假设。真正的约束是首次回填的一次性
推送，它受家庭上行带宽限制，可能需要数小时。上行带宽尚未测量，列入 §4 必测指标。

### 5.8 运行约束

- **运维人力是一个人，且是兼职。** 任何需要每批次人工介入的设计直接出局，这条比任何性能
  指标都更早地淘汰方案。
- MBP 不保证在线，日增量不得依赖它。
- 只有一套调度器，在 OCI，见[平台架构](platform-architecture.md) §4.2。
- compaction 独立排期，不顺带完成，且与增量写入错开，见 §5.4。
- 失败必须可重入。批次中断后重跑不得产生重复或半写状态。
