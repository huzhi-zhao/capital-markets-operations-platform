# ADR 0006: FIX 4.4 as the Single Protocol Baseline

> **Status**: Proposed · **Date**: 2026-09-12
>
> **Related requirement**: [监管与行业数据契约](../requirements/regulatory-data-contracts.md) §3.1、§3.3、§7
>
> **Related architecture**: [平台架构](../platform-architecture.md)

## Context

CMOP 的前台到中台这一段（订单、成交、分配、确认）用 FIX 承载。**协议版本必须在填任何一张
字段表之前定下来**，因为标签号、枚举取值与报文语义在版本之间并不等价：
同一个标签在两个版本里可以有不同的合法值集合，而**这类差异在数据落地之后才发现的话，
要重写的是全部已生成的报文与全部引用它们的字段表**。

[监管与行业数据契约](../requirements/regulatory-data-contracts.md) §3.1 已于 2026-09-09
作出选择并于 2026-09-10 按规范原文复核。**选择本身不在本 ADR 里重做**，
本 ADR 回答的是它为什么构成一项长期约束：

**CMOP 以哪一个 FIX 版本为准，是否允许混用，以及这条约束在什么条件下才可以被推翻。**

它满足 ADR 准入边界的两条：它建立了跨模块、跨阶段都必须遵守的数据契约；
**它一旦开始实施就代价高**——回滚意味着重写全部 FIX 侧数据。

## Options considered

**一、FIX 4.2。** 存量最大的老版本。

**二、FIX 4.4 with 20030618 Errata。** 勘误版，是取证时实际使用的文件。

**三、FIX 5.0 SP2 或 FIX Latest。** 最新版本线。

**四、多版本并存。** 同时生成两个版本的报文，用版本差异本身制造对账差异。

**五、FIXML。** XML 形态而非标签等号值形态。

## Decision

**采用 FIX 4.4 with 20030618 Errata，单版本，不混用。**
本项目所有标签号、枚举取值与语义一律以它为准。**引用其他版本的资料必须显式注明版本，
不得默认等价。**

### 选项一出局的理由是规范原文，不是印象

Volume 5 的 Allocation Instruction 一节明确称 **Confirmation 与 Allocation Report 是 4.4
新增的报文**，费用与开支的传达职责由分配指令移交给它们。**只要项目要讲"从订单一路对到
确认"，4.2 就不够用。**

**这里有一处此前的措辞不准，已更正并保留在契约文档里。** 分配语义并非 4.4 才有：
同一页写明 4.4 之前该报文名为 Allocation、其应答名为 Allocation ACK。
**4.4 新增的是确认，不是分配。** 核对日期 2026-09-10，出处 Volume 5 p. 12。

### 选项三出局的理由是它多出的能力对本项目无用

5.0 的主要改动是把会话层拆为独立的 FIXT。**本项目不运行 FIX 引擎**，
是把应用层报文批量生成落盘，**会话层价值为零**。其余扩展字段只增加需核对的表面积，
不增加工程难点。4.4 的真实存量也远大于 5.0。

**标准的现代性由 ISO 20022 承担**，结算与资金侧走 `sese`、`camt`、`pacs`，本就是当前标准。
**FIX 只需覆盖前台到中台这一段，而这一段是 4.4 最稳的地盘。**

### 选项五出局的理由恰恰是它更简单

标签等号值的裸格式加上嵌套重复组**是真实的工程难点**：分配类报文含分配明细、杂项费用、
参与方等多层重复组，摊平进 Silver 是外生问题，不是为演示制造的问题。
**FIXML 把这个难点交给了 XML 解析器，等于把项目要证明的那部分能力外包掉。**

### 选项四推迟，不否决

真实机构同时承接不同 FIX 版本的对手方流量，**版本差异本身制造对账差异**，
例如某字段一边有一边无、枚举集合不一致。这与
[原始数据源清单](../requirements/raw-data-source-inventory.md) §5.1 里两个官方汇率口径
属于同一类**外生的口径性差异**素材，**对主 BO 有真实价值**。

**推迟的理由是顺序，不是价值**：引入第二个版本要多读一份规范，会拖住字段表。
**先按单版本冻结，第一个纵切跑通后再评估。** 届时它是一次增量，不是一次返工，
因为本 ADR 要求的"引用其他版本必须显式注明"正是为此留的接口。

### 配套约束：只用标准标签，不自定义字段

遇到标准未覆盖的语义，**在契约文档里显式登记一条缺口并说明如何绕开，不得私自加用户
自定义标签**。

**这条不是风格偏好。** 私有标签会让整套报文失去"由公开规范推导"的可信度，
而**那正是合成事实数据可信的唯一支点**——CMOP 的数据是编的，它唯一能主张的是编得符合
公开规范。加一个只有自己知道含义的标签，这条主张就断了。

## Consequences

### Positive

- **字段表可以开始填。** 版本不定，任何一张字段表都是无主的，这正是本决定必须前置的原因。
- **版本差异素材没有被烧掉。** 选项四是推迟不是否决，且显式注明版本的要求为它留了接口。
- **可信度的支点被明确写下来了。** "不自定义字段"这条约束此前散在契约文档正文里，
  现在有了一个可以被引用的位置。

### Negative and risks

- **勘误版的选择带来一处长期的引用负担。** 版本串是 "4.4 with 20030618 Errata"，
  **不是 "4.4"**。任何一处简写成 4.4 的引用，日后都无法判断它指的是勘误前还是勘误后。
  契约文档 §7 已登记完整版本串，**引用时必须照抄**。
- **规范文本是第三方版权材料，不入库。** 本地副本在 `~/Downloads/fix-4-4-spec/`，
  仓库只保留引用。**因此本 ADR 的每一条证据都必须带卷号与页码**，否则无法复核。
- **单版本意味着 FIX 侧不会自然产生口径性差异。** 主 BO 需要的差异素材现在全部来自
  别处——汇率口径、时点基准、注入。**这不是缺陷，但它是一项已知的素材缺口**，
  在选项四落地之前一直存在。

### 与其他决策的关系

- [ADR 0002](0002-transaction-centric-lakehouse-layering.md) 的 Bronze 契约要求保留原始报文。
  本 ADR 决定了那些报文长什么样，**但不改变分层语义**。
- 本 ADR 不约束 ISO 20022 侧。两套标准各自选版本，**契约文档 §7 分行登记**。
