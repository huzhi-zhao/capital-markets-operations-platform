# ADR 0001: Project Boundaries and System Context

> **Status**: Proposed · **Date**: 2026-09-02
>
> **Related requirements**: [Project overview](../requirements/project-overview.md),
> [Business objectives](../requirements/business-objectives.md)

## Context

本项目的目的首先是证明企业级金融数据工程能力，而不是同时承载个人投资产品、量化研究
和多个行业方向。若不先固定系统边界，后续会在行情湖、交易运营平台、AI 特征平台和
Ghostfolio-AI 扩展之间反复摇摆，数据粒度与验收标准也无法收敛。

金融机构运营数据的核心事实通常是订单、成交、资金、持仓、清算与监管事件。行情、证券
主数据和公司行为很重要，但更适合作为估值与重述所需的参考数据，而不是唯一事实中心。

## Options considered

### A. 扩展 Ghostfolio-AI，同时承担金融业务与 TB 级数据工程

优点是项目数量少、可以复用部分金融语义。缺点是个人投资组合产品与资本市场运营平台的
用户、事实粒度和成功标准不同，合并后两个故事都会变得模糊。

### B. 建设以历史行情为核心的金融湖仓

公开数据容易获得，规模也容易放大。但主要展示的是采集和分析行情，不能自然覆盖清算、
对账、迟到确认、监管报送和逐笔追溯。

### C. 选择农业与地理空间大数据

真实公开数据充足，并可复用既有地理空间经验。但它与目标金融 IT 岗位、交易运营后端和
监管数据工程的直接关联较弱。

### D. 建设独立的交易运营数据工程平台

使用合成交易事实与真实公开维度，围绕对账、监管、重述和风险聚合建立系统。

## Proposed decision

采用方案 D，并提出以下项目边界：

1. CMOP 是独立于 Ghostfolio-AI 的资本市场运营数据平台。
2. orders、trades、cash movements、settlements 和 positions 是核心业务事实；行情是
   参考维度和估值输入。
3. 目标数据规模为 800 GB–1.5 TB，目的是迫使分区、增量、文件治理和 shuffle 设计接受
   真实检验，而不是追求最大字节数。
4. 私有事实使用可复现的参数化生成器合成；证券、公司行为、行情、SEC XBRL、汇率和
   利率等优先采用真实公开数据。
5. 项目不包含 alpha、自动交易或 AI 量化研究；ML 最多作为 Silver 宽扫描与特征工程的
   支持性工作负载。
6. 农业方向不保留为并行方案。

本决定在 `Proposed` 阶段仍可随着主 BO 收敛而修改。

## Consequences

### Positive

- 项目叙事集中于金融数据工程，而不是泛化的大数据演示。
- 迟到数据、对账、历史重述、血缘和监管追溯都由业务问题自然产生。
- Ghostfolio-AI 与 CMOP 各自证明不同能力，避免一个项目承担冲突目标。
- 合成数据的设计、约束和透明标注本身成为可展示能力。

### Negative and risks

- 高保真生成器需要在编码前投入较长时间制定分布、不变量和异常注入规则。
- 真实交易生产数据不可用于校准，统计合理性必须通过公开资料和显式假设说明。
- 系统容易被技术卖点带偏，因此 BO 必须先于 Gold schema 和展示层冻结。

## Open questions

- 主 BO 最终是对账异常、监管报送，还是以两者结合形成运营控制主线。
- 项目模拟的机构边界是 broker-dealer、银行资本市场部门还是抽象运营平台。
- 证券与账户产品范围需要多宽，才能支撑业务复杂度而不变成金融产品百科。
