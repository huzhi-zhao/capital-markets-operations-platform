# ADR 0009: Probes as Declared Steps Under tools

> **Status**: Proposed · **Date**: 2026-09-14
>
> **Related ADR**: [ADR 0008 代理执行权限与分阶段授权](0008-agent-execution-authority-and-staged-grants.md)
>
> **Related method**: [立项与就绪度](../project-inception-and-readiness.md) §5、
> [roadmap](../roadmap.md) 的"probe 例外"
>
> **执行状态**：**只定方案，未建立任何目录或执行器。**

## Context

[立项与就绪度](../project-inception-and-readiness.md) §5 要求每个 probe 事先写明输入、阈值与
停止条件，并保存环境、版本、配置和关键测量值。仓库协作规范同时规定**探测脚本与临时输出不进仓库**，
唯一例外是产出被文档引用的参考数据的抽取脚本。

这两条在规模变大后开始互相拉扯：

1. **探测规模上了一个数量级。** 下一阶段一轮 EDA 预计含几十至上百条 SQL、数百次 CLI，
   多数是同一个模式套在很多张表、很多台主机上。散落在会话临时目录里的命令**无法重跑，也无法对比**。
2. **数字变了，分不清是数据变了还是 SQL 变了。** 两次运行之间没有可 diff 的定义与结果摘要。
3. **[ADR 0008](0008-agent-execution-authority-and-staged-grants.md) 要求代理只通过受控入口执行。**
   受控入口需要一份人能 review 的定义，而会话临时目录里的东西人看不到。

**问题**：探测的定义放在哪，以什么形态执行，哪些进仓库、哪些不进。

## Options considered

**一、维持现状。** 探测命令留在会话临时目录，逐条执行。

**二、放进核心域目录**，例如 `generator/`、`validation/` 或新建 `scripts/`。

**三、Notebook**，例如参数化执行的 Jupyter，或纯 Python 文件形态的 notebook。

**四、编排器**，例如 Dagster、Kestra，或复用共享主机上的 Airflow。

**五、声明式步骤加通用执行器，放在 `tools/` 边缘目录。**

## Decision

**采用选项五。**

### 一、位置

| 路径 | 内容 |
|---|---|
| `tools/probe-runner/` | 通用执行器，所有 probe 共用 |
| `tools/probes/<probe-id>/` | 每个 probe 一个目录 |

**核心域目录不引用 `tools/probes/` 下的任何内容。** Phase 1 需要的能力在核心域重新实现，
不从 probe 目录迁移，与 §5 第四条"默认视为可丢弃代码"一致。

### 二、每个 probe 目录的内容

| 内容 | 是否进 git | 说明 |
|---|---|---|
| 章程 | 是 | 问题、关联风险、输入、阈值、停止条件，对应 §5 第一、二条 |
| 步骤清单 | 是 | 顺序、执行位置、参数、超时、按上一步结果展开的规则 |
| 步骤文件 | 是 | SQL 与 shell，一步一个文件 |
| 运行摘要 | 是 | 每次运行的代码版本、时间、每步耗时、行数与步骤文件哈希 |
| 原始结果 | **否** | 放在仓库以外；被文档引用为参考数据时，按 `data/reference/` 的现行规则处理 |

**摘要进仓库，所以摘要只写逻辑节点名**（NAS、MBP、OCI），不写主机地址、内网地址、
用户名或凭据位置。这是公开仓库规则的直接推论。

### 三、执行器的契约

本 ADR 只约束行为，不约束实现：

1. 一轮探测是一次调用，按清单顺序执行全部步骤。
2. **参数展开**：同一模式作用于多张表或多台主机时，写一个步骤加展开规则，不逐条手写。
3. 某一步失败即停，修复后可从断点续跑。
4. SQL 默认带超时；**对大表缺少分区谓词或行数上限的查询拒绝执行**。
5. 只使用 [ADR 0008](0008-agent-execution-authority-and-staged-grants.md) 规定的专用身份，
   执行器本身属于"探测"类入口。
6. 两次运行的摘要可以直接 diff，能区分数据变化与步骤变化。

执行器的语言、命令入口工具与远程执行库都不在本 ADR 选定。

### 四、与仓库协作规范的关系

**本 ADR 不推翻那条规则的意图，而是细化它**：临时输出仍不进仓库，探测代码仍不进核心域。
变化只有一处：**探测的定义与摘要作为结论的出处进 `tools/`**。这与现行例外同源，
区分标准都是"产物有没有被文档引用"。

本 ADR 被接受时，在同一次变更里修改仓库协作规范的对应条目。**Proposed 期间不改。**

### 为什么不选其他选项

- **选项一**：规模上去之后无法重跑、无法对比，也无法成为受控入口。
- **选项二**：把一次性代码与生产代码放在一起，违反 §5 第四条，日后很难分清哪些可以删。
- **选项三**：交互体验好，但跨多台主机的远程步骤不自然，结果混在文件里，diff 效果差。
- **选项四**：编排器是常驻组件，与 roadmap"不搭建管道组件"冲突；共享的 Airflow 属于 UOIP，
  拿来跑 CMOP 的临时探测会扩大爆炸半径。**探索流程出现跨机器强依赖和调度需求时再评估。**

## Consequences

### Positive

- 一轮探测变成一次调用，代理写定义、执行、读摘要，人审结论。
- 章程、步骤与摘要在同一个目录里，review 一次看全。
- 摘要可 diff，"数字过期"一类问题可以在两次运行之间定位到原因。

### Negative and risks

- **执行器要自己维护。** 规模预计几百行，但它会成为所有探测共同依赖的一段代码。
- **`tools/` 会持续增长**，需要一个索引说明哪些 probe 已完成、已冻结。
- 摘要进公开仓库，**脱敏靠执行器的输出约定**，约定失效就会泄露环境信息。

### 本决定会在什么条件下被推翻

1. 若探测主要变成跨机器、有依赖、需要定时重跑的流程，选项四重新成为候选。
2. 若后续 probe 数量很少，执行器的维护成本高于收益，退回到逐个 probe 的独立脚本。

## Open questions

- probe 编号规则，以及与 TODO 或需求文档中已有探测编号的对应方式。
- `tools/probes/` 的索引放在哪里、记录哪些状态。
- 原始结果在本机的默认落点与清理策略。
